# 请求装配、TLS 与批量运行

> 从 `AGENTS.md` 拆出的按需文档，原文逐字保留。只有动到本域时才需要读它。

**HTTP 请求绕过 webview 的 CORS**：`src/lib/http.ts::sendRequest` → `httpRequest` 命令 → `http_executor.rs`（reqwest）。

**请求体的两份内容：`content` 是载荷，`schema` 是定义.** `RequestBody` 有两个字段回答不同的问题：`content` 是这一次发出的载荷，`schema` 是文档里那份参数定义（JSON Schema，只用于文档与 OpenAPI 导出，**从不上线**）。两者都是 JSON 对象、形状接近，合成一个输入框时 AI 写接口定义就会把 Schema 当载荷发出去。故界面给它们两个编辑器（`BodyEditor.tsx` 的左边载荷区与右边 Schema 区，两者并排常驻），MCP 侧的工具描述逐字写明哪个字段放什么，并在 `endpoint_create` / `endpoint_update` 上设一道门：`RequestBody::payload_may_be_a_schema` 判定载荷「看起来是一份 Schema 且 `schema` 还空着」时拒收（`api_validate_endpoint` 报同一条 issue）。真要把一份 Schema 当载荷发时，把同样的内容也写进 `schema` 即可 —— 那是声明意图，不是写反。**残留的 schema 两边都要看得见**：模式切成 `none` 之后 body 里的 schema 仍在（模式切换保留整个 body），界面因此要在 `none` 下仍给出那块 Schema 区（否则用户删不掉它），导出侧则只在真的要写 `requestBody` 时才收集 schema（`mode = none` 的端点没有 requestBody 可引用，收集了就是 `components.schemas` 里没人引用的孤儿定义）。**GraphQL 端点的正文不来自 `content`**：协议为 `graphql` 时它由 query / variables 组装，组装失败就是 `body: null` + `problems` 非空（发送入口据此拦下）；导出时这份 `schema` 也不沿用——投影把它置空并落一条 info 诊断。

**响应的固定参考信息：`responses` 是文档，不是行为.** 与 `RequestBody` 的两份内容对称，`EndpointDetail.responses` 回答「这个接口会回什么」：每条 `ResponseDefinition` 有状态码（`200` / `2XX` / `default`）、说明、media type、响应正文的 JSON Schema 与示例原文。**它不上线**——发送链路上没有任何一处读它；也**不从 `response_history` 反推**：历史只记录发生过的事，不替用户声明契约。校验只有一处实现（`domain::response_problems`，REST 与 MCP 共用）：状态码写法、同份内不得重复、`schema` 必须是对象、`contentType` 必须是 `type/subtype`。OpenAPI 导出里 `responses` **不再合成**：端点有定义就用定义（`contentType` 空只写 `description`，写不进文档的那条落诊断并跳过），一条定义都没有才退回 `200: {description: "OK"}`。

**响应区左栏画的是线上那一份，不是界面上拼的那份.** 响应区分左右两栏：左栏是这一次实际发出去的请求（`RequestSummary`），右栏是收回来的响应，两栏描述同一次调用。**请求头那一段必须是线上那一份** —— 传输层还会补上 `accept` / `accept-encoding` / `host` / `content-length`，界面上写的那几条只是其中一部分。后端 executor 因此在请求发出后把补齐后的请求头报上来（`HttpResponse.request_headers`，由 `http_executor.rs::effective_request_headers` 拼），前端快照优先用它（`requestInput.ts::toRequestSnapshot`），请求从未抵达（超时 / 网络错误 / 中止）时才回落到界面上拼的那几条。**这个值不许靠猜**：`http_executor_test.rs` 用裸 TCP 抓原始请求字节，与上报的值逐条（含顺序）比对，写错一个值那条测试就红。`accept-encoding` 取线路上的原样（逗号后没有空格），不是人读的写法。

**存进历史的那份请求是解析之后的那一份.** 落库的 `StoredRequestSnapshot` 存的是 base URL 已拼接、路径参数已替换、`{{var}}` 已换成取到的值、查询串已追加的那一份。文档里那份模板随时可以再打开看，线上发出去的那一份只有存下来才不会丢。**OAuth2 的 token 只在发出去的那一份里**（预览刻意不含它，否则 cURL 预览会把活凭据渲染进可复制的命令行），故快照取 `sendPreparedRequest` 返回的 `outbound` 而不是 `prepared`。

**收藏与保留条数是两条独立的规则.** 收藏的行永久保留，不参与裁剪；每个接口保留多少条**未收藏**的历史由全局偏好 `response_history.keep` 控制（`preferences` 表的一行，跨项目生效），改这个条数立刻裁库（`trim_all` 只删未收藏行）。界面上的本地列表用同一条规则裁一次（`history-keep.ts::capUnfavorited`），否则屏幕上的行数与库里对不上。`clear` 同样只删未收藏行，界面文案写的是「清空未收藏」。这个条数是**全局的**，故它不在出站请求旋钮那一组里，单独一张卡片。

**请求的装配有两条路径，各自有明确的边界.** 渲染进程组装「这一次发什么」（草稿的未保存编辑只有它知道），后端组装「这个端点是什么」（落库的行）。两条路径的**规则**必须逐条相同，而规则写在两处（TS 的 `prepareRequest` 与 Rust 的 `resolve_endpoint`）—— 故它们由共享样本钉住：`fixtures/resolve-parity.json`（两侧读取器为 `src/lib/__tests__/http-build-parity.test.ts` / `crates/simple-post-mcp/src/variable_fill/resolve_parity_test.rs`）与 `fixtures/body-parity.json`（`src/lib/__tests__/body-parity.test.ts` / `crates/simple-post-core/src/body_parity_test.rs`）。multipart 的装配（boundary、分片头、文件字节）只有一份实现：`crates/simple-post-core/src/multipart.rs`，桌面、`serve-web` 与 MCP 都走它。**改动任何一条规则就改两处**，否则样本会红。 `fixtures/resolve-parity.json` 有 20 条用例，其中两条带路径改写规则：它们把「路径改写 → 拼接 → 模板替换 → 斜杠收拢」这个次序钉住，并钉住「命中首条改写后不再串联后续规则」。两侧的组装路径各写一遍那个次序，只有一侧改了次序时，这条用例会红。三条易忘的细节：query 里的空格编码成 `%20`（Rust 的 `core::url::percent_encode`，与 JS 的 `encodeURIComponent` 同字符集，**不是** form 编码的 `+`）；multipart 的 `Content-Type` 追加在 header 列表**末尾**（用户自己写过则只留第一条就地替换其值，其余重名行丢弃）；空 key 的参数不参与查询串，其中的变量也**不**报缺失。

**四种协议共用一条装配路径，会话式传输各有一条边界.** `RequestProtocol` 的线格式取值是 `http` / `graphql` / `sse` / `websocket`，存在 `endpoint_details.protocol` 列（`graphql_json` 存 GraphQL 配置）；解析器只接受这四个值，未知取值反序列化报错，不回落成 `http`。GraphQL 的请求体由同一套规则在两侧拼出：渲染进程的 `src/lib/http-build/prepare.ts` 与 MCP 的 `crates/simple-post-mcp/src/variable_fill/resolve.rs::graphql_payload`。规则是：query 与 variables 都做 `{{var}}` 替换；variables 原文 trim 空则不带键，非空必须是 JSON 对象；operationName 的 trim 只用作空判定，写进 payload 的是 trim 后的串（trim 空不带键）；payload 键序为 query → variables → operationName；method 固定 `POST`；`Content-Type` 只在用户**启用**的行里判断，缺省补 `application/json`。共享样本 `fixtures/graphql-parity.json` 是这两侧唯一的钉子（读取器是 `src/lib/__tests__/graphql-parity.test.ts` 与 `crates/simple-post-mcp/src/variable_fill/graphql_parity_test.rs`）；改任何一条规则就改两处。SSE 的事件流由渲染层消费，**服务端不写响应历史**（`crates/simple-post-server/src/web_api/routes/stream.rs` 的注释写明 `endpointId` 只收下不使用）：一次会话只允许一行历史，写入发生在渲染层收到 `end` 时。web 形态停止一条流走「`DELETE` 取消 → 等收尾事件 → 宽限后才 abort」（`src/lib/stream-transport/web.ts`）；先 abort 会让收尾事件到不了渲染层，面板停在 streaming 且不写历史。渲染层的布局契约是 SSE 只替换「响应」页的内容（`src/features/http-tester/tabs/TesterShell.tsx` 里页签条与 `RequestTabPanels` 在 SSE 下仍然渲染），故参数 / 请求头 / 鉴权页照常可用；把整个右栏换成事件流会让用户无法为这条流改请求头。WS 共用同一条布局契约：`wsSurface` 只在 `tab === 'response'` 时替换响应页（换成帧面板），页签条与 Params / Headers / Body / Auth / TLS / 路径参数页仍是 `RequestTabPanels`，只有 URL 栏隐藏——面板自带地址与连接按钮，同一条地址不能有两个输入框。WebSocket 的会话登记在 `crates/simple-post-core/src/ws.rs`。`connect` 是同步函数：返回时写端已登记，紧接着的 `send` 不会撞 `NotFound`。TLS 经 `tls::resolve(全局, 端点)` 合成，与 HTTP 共用同一份 `TlsSettings`：`skip_verify` 整份替换校验器（此时内置根不参与），否则内置 Mozilla 根在前、自定义 CA 追加在后，客户端证书与私钥必须成对。流式建连前只补 OAuth2 token（`src/features/http-tester/stream/stream-auth.ts`）；Bearer、Basic、API key 已经在 `prepareRequest` 的 header 里。WS 不跑请求脚本。MCP 只能发 HTTP 与 GraphQL：`crates/simple-post-mcp/src/mcp/http_ops/mod.rs::unsupported_protocol` 在权限门**之后**拦 `api_call_endpoint`（无权限者不该从错误文案里探测端点协议），`api_run_request` 的协议由调用方自己传、在解析入参时就拒，`api_run_collection` 把这类端点记进 `blocked`（报告里的 `not_run` 仍是 0）。GraphQL 补全靠按需拉 introspection：`src/lib/graphql-schema.ts` 的 `INTROSPECTION_QUERY`、`parseIntrospection` 与 `completionCandidates` 负责查询体、解析与候选计算。接线在 `src/features/http-tester/graphql/use-graphql-schema.ts`：它按需拉取并在会话内缓存（键是 `endpointId|url`，不落盘），只有点了面板上的按钮才发 introspection 请求；补全来源经 `EditorState.languageData.of(() => [{ autocomplete }])` 挂进查询编辑器（自动补全扩展本身由 `@uiw/react-codemirror` 的 basicSetup 装上），故不新增 `@codemirror/autocomplete` 直依赖；Variables 编辑器不挂补全。查询历史从响应历史行的请求体反推（`src/features/http-tester/graphql/query-history.ts::pickQueryHistory`），不新增存储。服务端关掉 introspection 时补全不可用，请求本身不受影响。

**请求体有七种形态，每种形态的内容形状与产物都不同.** `BodyMode` 的七个变体在 `RequestBody.content` 里装的东西不一样：`none` 装空、`json` / `xml` / `raw` 装原文、`form` 装行数组的 JSON 文本、`multipart` 装分片数组的 JSON 文本、`binary` 装文件描述的 JSON 文本。`form` 与 `multipart` 是**结构化**的：表格里的「说明」列有地方放，文件分片有地方放路径（桌面与 MCP）或字节数 `size`（浏览器上传）。这套规则写在两处（Rust 的 `core::body` 与 TS 的 `src/lib/body`），由 `fixtures/body-parity.json` 钉住（读取器是 `crates/simple-post-core/src/body_parity_test.rs` 与 `src/lib/__tests__/body-parity.test.ts`）。文件分片的判据由 Rust `core::multipart::is_file_part` 与 TS `src/lib/body/index.ts::isFilePart` 共用同一条规则：**非空 `path` 或存在 `size`**；`path: ""` 且无 `size` 的分片是文本分片（界面上「切到文件但没选文件」只存在 `BodyTables.tsx` 的 `pendingFiles` 本地状态里，不写进 `content`；前端 `MultipartPart.size` 只在浏览器上传时出现，`parseMultipartParts` 会读取它）。`core::body::resolve_multipart_body` 与 TS `resolveMultipartBody` 都调用 `is_file_part` / `isFilePart`，因此文件分片（含浏览器上传）与 `binary` 的文件描述都不进模板化；字节由 `core::multipart::OutboundBody` 在发送时按路径现读或从上传通道接力，故大文件不进请求 JSON、不进历史快照。零字节浏览器文件（`size === 0` 且 `path` 为空）仍按上传处理，不回落到按路径读盘。cURL 渲染（`src/lib/http-build/curl.ts`）在桌面形态渲染真实路径（`-F 名字=@路径`、`--data-binary @路径`），浏览器上传分片渲染成 `-F 名字=@文件名`（`binary` 同理 `--data-binary @文件名`）并附带提示行，说明需在文件所在目录执行或替换为本机路径。四条易忘的细节：**模板化按字段做**——`form` 与 `multipart` 逐个字段替换，整段替换会把替换值里的引号塞进那段 JSON 文本，于是整份内容解析不出来、请求发出去的是空 body；`json` / `xml` / `raw` 才整段替换；`binary` 不替换（文件字节不是模板）。**空键与停用行不进正文**，其中的变量也**不**报缺失——没有名字的字段没有地方可去。**`form` 的内容读不出行数组时按旧格式读**（早期版本存的是一个拼好的 urlencoded 串，Postman 导入器至今还那么写），那份内容不该被当成空表单。**`binary` 的 Content-Type 取文件自己的 MIME 类型**，缺省 `application/octet-stream`。
**渲染进程在组装请求前把落单的代理项归一成 U+FFFD.** JS 字符串按 UTF-16 存，用户能写进一个落单的代理项（UTF-16 的 D800–DFFF 里没有配对的那一个），而它在 UTF-8 里没有对应字节。平台的 `encodeURIComponent` 遇到它直接抛 `URIError`，而请求是在渲染期组装的（`HttpTester` 的 `useMemo`），仓库里没有 React 错误边界，异常一路到 React 根节点、整棵工作区树被卸载。故 `src/lib/well-formed.ts::wellFormed` 先把落单的代理项换成 U+FFFD，`src/lib/percent-encode.ts::percentEncode` 是那个不抛异常的百分号编码原语，`prepareRequest` 在组装前用 `wellFormedDeep` 把入参逐字段归一。**Rust 侧不需要这一步**：Rust 的 `String` 恒为合法 UTF-8，serde_json 遇到 JSON 里的落单代理项转义直接报错，故 `core::body` 收不到这种值 —— 两条规则不对称的原因就是这一条。共享样本 `fixtures/body-parity.json` 装不下这个用例（那份样本是 JSON，serde_json 读不了），它由 `src/lib/__tests__/lone-surrogate-encoding.test.ts` 与 `crates/simple-post-core/src/body_test.rs` 里那条用例分别钉住。

**请求侧以文本描述为主、浏览器上传走随请求分片流，响应侧保留 `body` 与 `bodyBase64` 两条互斥通道.** 桌面端与 MCP 形态不走文件上传：`HttpRequestInput` 只带 `body` 与 `body_mode`，`multipart` 与 `binary` 交出去的是含绝对路径的描述文本，`core::multipart` 在发送前装配并按路径流式读盘。浏览器形态（`serve-web`）下 `<input type="file">` 只有 `File` 句柄、没有服务端可读路径（`src/lib/pick-file.ts`），因此 `src/lib/web-uploads.ts` 按「文件名 + 字节数」暂存 `File`（`rememberUpload`），发送时 `uploadFiles` 按请求体里文件分片出现的顺序取文件（非空 `path` 跳过），`uploadForm` 打包为 `multipart/form-data`：第一个分片恒为 `request`（JSON 信封，文件分片带 `path: ""` 与 `size`），其余分片按顺序为各文件字节。前端常量 `src/lib/tauri-commands/web-routes.ts::UPLOAD_ROUTES` 对应服务端三条 `internal` 上传路由（`crates/simple-post-server/src/web_api/router.rs`、`routes/upload.rs`）：`POST /api/http/send-upload`、`POST /api/http/send-upload-progress`、`POST /api/http/stream-upload`。服务端先读全 `request` 信封，随后边收边将文件字节转为 `UploadFrame::{Part, Data, End}` 经有界队列（容量 `4`）交给执行器，不落盘、不整段进内存。上传路由的 axum `DefaultBodyLimit` 为 `128 MiB + MAX_REQUEST_BODY_BYTES`（64 MiB），`core::http_executor::outbound_body` 对装配后的 multipart 总长与 `binary` 上传的 `size` 均校验 `MAX_REQUEST_BODY_BYTES`，使桌面与浏览器保持同一语义上限。`core::multipart::assemble_inner` 在带上传通道却没有任何声明了 `size` 的文件分片时，于装配期报错 `the request carries uploaded files, but its body declares none`（先于发包）；`core::http_executor::reject_extra_uploads` 对不消费上传字节的请求体（`json`/`form`/`xml`/`raw`、按磁盘路径读的 `binary`、空 body）在发包前检查上传通道，收到帧即报同一条错误（空通道不算违约；这次等待受请求的 `timeoutMs` 约束，超时同样按这条错误收尾，半开连接不会把 handler 与 pump 一直占住）。`web_api::routes::upload::pump` 会把信封未声明的多余分片读入并丢弃，`Content-Length` 与实际发出的字节只由信封里声明的 `size` 决定。`http_executor::describe_reqwest_error` 将 `error.source()` 链拼进错误消息，流式路线（`core::stream`）复用它报告 reqwest 发送错误，使「上传字节比声明短/长」或路径不可读等流式错误能直接呈现。两种形态下 `multipart` 的 `Content-Type` 均由 `core::multipart` 现生成并覆盖调用方写的值，`content-length` 用装配后的精确值；历史 `request_json` 只存描述文本（不存文件字节），不涨 `SCHEMA_VERSION`、无迁移。**响应的形态判据先看 Content-Type，再看字节**：读回来的字节是按体积上限裁过的，裁点落在多字节字符中间时，一个纯文本响应读回来也是非法 UTF-8，只看字节会把文本误判成二进制。界面按这个结果选视图：JSON 走美化视图，文本原样显示，图片给预览，其余给下载（`src/features/response-viewer/responseKind.ts`）。响应一旦判成二进制，`body` 是**空串**而不是宽松解码后的残影（非法字节换成 U+FFFD 会把二进制弄坏且不可恢复），原始字节只能从 `bodyBase64` 取；文本响应（含按 Content-Type 判成文本、但字节不是合法 UTF-8 的那一种）走 `body`，不给 `bodyBase64`。

**base URL 的解析与路径前缀改写、OAuth2 的 token 注入同样各写两遍，故也由共享样本钉住.** base URL 的解析规则写在渲染进程侧的 `src/lib/url.ts::resolveEndpointBaseUrl` 与 MCP 侧的 `crates/simple-post-mcp/src/variable_fill/base_url.rs::resolve_base_url`；**路径前缀改写**的实现住在核心库的 `crates/simple-post-core/src/url.rs::apply_rewrites`（按顺序匹配、命中首条即停止；MCP 侧与导入导出侧都转发到它，那两处再写一份就会分叉）；OAuth2 的 token **注入**规则写在渲染进程侧的 `src/lib/oauth2.ts::applyOAuth2Token` 与 core 侧的 `crates/simple-post-core/src/oauth2/inject.rs::inject`。两边的**结果**必须一致，否则界面预览的请求与真正发出去的请求不是同一个。样本是 `fixtures/base-url-parity.json`（解析 11 条 + 改写 18 条，改写那组钉住「命中首条不再串联」与根 / 具体前缀的先后）与 `fixtures/oauth2-parity.json`（13 条），两侧各有一个读取器（`src/lib/__tests__/base-url-parity.test.ts` / `crates/simple-post-mcp/src/variable_fill/base_url_parity_test.rs`，OAuth2 那对在 `src/lib/__tests__/oauth2-parity.test.ts` / `crates/simple-post-core/src/oauth2/inject_parity_test.rs`）。OAuth2 的**配置替换**规则只有一份，见下一段。**改动任何一条规则就改两处**，否则样本会红。两侧的读取器都要 `deny_unknown_fields` 并数一遍条目数——键名漂了会让整条测试静默空转。九条易忘的细节：base URL 的**解析没有回退层** —— 端点自己的 `baseUrlOverride` 优先，它在场时那一格的**改写规则照样生效**（规则改的是端点自己的路径，与主机是谁的无关）；否则读环境里「环境 × 模块」那一格，格子缺失或地址为空就是「没有地址」；`source` 报的是**地址从哪来**（`override` 是端点自己点名，`module` 是模块那一格，`none` 是什么都没有），不是哪个格子提供了值；**改写是路径前缀替换** —— 端点自己 URL 的路径前缀从起点换成目标，模块地址自带的路径段不参与匹配，命中必须落在路径边界上（`/`），否则 `/api/air` 会误命中 `/api/airplane`；起点按原文匹配（不做 `{{var}}` 替换），目标里的 `{{var}}` 照常替换；**目标是绝对地址时拒绝改写** —— 改写只准改路径，不准把请求挪到另一个主机上去；**起点是 `/` 时它指的是路径根**，整条路径换到目标底下；端点自带完整地址时，改写作用在它的**路径**上，主机与查询串一概不动；；起点按原文匹配（不做 `{{var}}` 替换），目标里的 `{{var}}` 照常替换；次序是**路径改写 → 拼接 → 模板替换 → 斜杠收拢**；OAuth2 的 `token_type` **去掉首尾空白后透传**（`MAC` 不改成 `Bearer`），去空白后是空串时只放裸 token，而 query 档按 RFC 6749 §8.3 只带裸 `access_token`（不带 token 类型）；query 档的**参数名**：判定「是不是空白」用去空白后的值，取值用**未去空白的原值**，故 `" id_token "` 这样的参数名会带着空白进查询串（被编码成 `%20id_token%20`）；header 档**不覆盖**用户自己写的 `Authorization`（大小写不敏感），query 档的参数名与 token 值都过 `encodeURIComponent` 那一套字符集。

**OAuth2 配置里的 `{{var}}` 只有一处替换，故那条规则只写一次.** 被替换的是四个字段：token 端点、授权端点、client id 与 scope。`clientSecret` / `password` / `authCode` 三个密钥与一次性输入**刻意不替换** —— 解出来的值会顺着这份配置进 token 请求，而那份配置会被 MCP 的 `api_resolve_endpoint` 回显给 AI 客户端，故少替换几个字段换来密钥不被解析层复制。替换规则住在 core 的 `crates/simple-post-core/src/oauth2/config.rs::substitute_config`，渲染进程与 MCP 都不自己替换：两边把**变量池**交给 core —— 渲染进程送的是 `PreparedRequest.vars`（与发送请求用的是同一份），MCP 送的是 `ResolvedEndpoint.vars`（取 token 要用的就是它）。两侧的字段清单由 `fixtures/oauth2-config-parity.json` 钉住（读取器是 `crates/simple-post-core/src/oauth2/config_parity_test.rs` 与 `src/lib/__tests__/oauth2-config-parity.test.ts`）。改动那份清单就改两处，否则样本会红。

**「当前环境」不是落库的状态，接口也不再绑环境.** 「当前环境」是每个客户端自己的实时状态：桌面窗口与网页标签各有一份，各切各的。落库会让 web 端多个人互相踩——一个人切了环境，另一个人发请求就换了地址与端口。故 `environments` 表没有 `is_active` 列（只有 `created_at`），`endpoint_details` 表没有 `environment_id` 列，MCP 工具 `env_set_active` 与 REST 路由 `POST /api/environments/active` 都不存在（`env_get_active` 改叫 `env_get_default`）。接口解析地址时读的是客户端的当前环境，故**切一次环境，全部接口一起换地址与端口**——这正是「新建环境并切换后端口不跟着换」那个问题的正解。

**默认环境 = 一个项目里最早创建的那个环境**（`environments.created_at` 认定；`db::environments::get_default` 按 `created_at ASC, id ASC LIMIT 1` 取，同一毫秒里创建的两个按 id 决胜）。它是**项目的属性**，不是用户的当前选择。MCP 侧发端点时按「本次调用点名的环境 → 项目默认环境」回落（`mcp::resolve_env`）：`api_call_endpoint` / `api_resolve_endpoint` / `api_validate_endpoint` 都接受可选的 `environment_id`，不点名就用默认环境。界面侧多一步「记住的那个」：`src/lib/env-default.ts::pickCurrentEnvironment` 按「记住的那个 → 默认环境」取，记住的那个只存在本机。**两边只在「都用默认环境」时给出同一个环境**：界面记住了非默认的环境时，MCP 那次不点名用的仍是默认环境，两者不同是本设计允许的 —— MCP 的环境逐次点名，界面看不到那一层；要让两者一致，只能由调用方在 MCP 侧显式点名界面上那个环境。**两个发送工具的环境参数名不一样，回落规则也不一样.** `api_call_endpoint` 收 `environment_id`，省略它就回落到**端点所属项目**的默认环境（端点能推出项目）；`api_run_request` 收 `env_id`，**没有回落** —— 临时请求没有端点行可读，项目归属只能由环境 id 反查，故省略 `env_id` 就是没有环境：那次请求没有 base URL、`{{var}}` 也不替换。写错名字不会报错（那两个入参结构都没有 `deny_unknown_fields`），`api_call_endpoint` 收下 `env_id` 会静默按默认环境解析，`api_run_request` 收下 `environment_id` 则是静默地没有环境。**点名的环境已经被删掉时不回落默认环境**：那一次请求没有环境（没有 base URL、变量不替换），`env_delete` 的工具描述与 `resolve_env` 的文档都这么写。

**请求旋钮仍要落库**（超时 / 跟随重定向 / 响应体积上限）：存在 `preferences` 表的 `request_settings` 行里（`db::preferences::keys::REQUEST_SETTINGS`），界面在设置面板里改它，MCP 侧发请求时读同一行；两侧的缺省值都是 5120 KB。**同名的那张 `request_settings` 表已被清除**：它从建立起就没有任何读者，现役容器只有 `preferences` 表里的这一行。
**批量运行的端点清单由共享样本钉住.** 一个容器下面的接口清单有两个实现：Rust 侧的 `db::nodes::ordered_subtree_endpoints`（MCP 的 `api_run_collection` 用它）与 TS 侧的 `src/features/batch-run/model/collect.ts::collectSubtreeEndpoints`（界面用它）。清单规则就是「界面渲染的那套顺序」：**容器直接持有的接口先出**，然后才是它的子集合，逐个递归展开 —— 不是纯 DFS 前序（那样子集合的接口会排在该容器自己的接口之前）。兄弟之间按 `(sort_order, id)` 排。样本是 `fixtures/collection-order-parity.json`，两侧各有一个读取器（`crates/simple-post-core/src/db/nodes_read_test.rs` / `src/features/batch-run/__tests__/collect.test.ts`）。**改动任何一条顺序规则就改两处**，否则样本会红。

**批量运行复用单次发送的组装逻辑，不另写一套.** 应用内每一条走 `endpointParts.ts::buildEndpointRequestParts` → `prepareRequest` → `sendPreparedRequest`，与用户手动点「发送」同一条通路（含脚本链与响应落历史）；MCP 侧每一条走 `variable_fill::resolve_endpoint_with`，与 `api_call_endpoint` 同一个解析器。批量层只负责「按什么顺序跑哪几条」「每条的结果怎么归类」，不碰请求怎么拼。

**批量报告的四类结论互斥且穷尽，但两侧的字段名与「压根没发出去」的判定不同.** 恒等式两边一样：`总数 = 状态码分布之和 + 没拿到响应 + 压根没发出去 + 未执行`；`未执行` 不并进 `失败` —— 中止掉的条目与失败的条目对调用方是两种不同的信息。成功的判据是 HTTP 2xx。缺变量**不拦**（照发，与单次发送一致），缺路径参数**拦下那一条**（不中断整批）。**应用内**（`src/features/batch-run/model/report.ts`）用 camelCase：`statusCounts` / `noResponse` / `blocked` / `notRun`；它的 `blocked` 多一种情形 —— 请求体解析不出来的那些条，因为界面侧发出去之前先过 `validateRequest`，与单次发送是同一道门。**MCP**（`crates/simple-post-mcp/src/mcp/http_ops/batch.rs`）用 snake_case：`status_counts` / `no_response` / `blocked` / `not_run`；它的 `blocked` 覆盖缺路径参数与**准备阶段失败**（缺请求配置、端点所属模块查不到、动态变量取不到值、请求解析不出来）—— 这一类是压根没发出去的，故不能记进 `no_response`（后者说的是交出去了但没回音）。MCP 侧**不**解析请求体 JSON，请求体是不透明字符串，解析不了的那条会照发出去，并按服务端的 4xx 计入 `status_counts`。把两侧的字段名与判定写成同一套，下一个 agent 就会照着界面那套去读 MCP 的返回值。

**批量运行是顺序的，不做并发.** 环境变量的写回由脚本产生，并发时写回的先后不可预期，报告也就不可复现；顺序执行时「第几条看到的是哪一份变量」是确定的。批次开始时复制一份环境快照，整批都用副本：脚本写回仍然落库，但不渗进后面那几条。

**HTTPS 出站设置分两层，合成只有一处。** 全局默认住在 `preferences` 表的 `request_settings` 行里（`RequestSettings.tls`），界面在设置面板的「请求行为」小节里改它；端点自带的住在 `endpoint_details.tls_json` 列里（`EndpointDetail.tls`），`NULL` = 继承全局默认。**端点给了设置就整体取代全局那份**，不是逐字段合并 —— 逐字段合并要求每个字段带「继承 / 自定义 / 清空」三态，界面上多出三倍的开关，且「端点清掉全局的 CA 路径」与「端点没配 CA 路径」在存储上无法区分。合成只有一处：`core::tls::resolve(global, endpoint)`，由 `script::send_with_scripts` 调；桌面端与 REST 端交出「端点自带的」，MCP 端交出「端点自带的或本次调用的覆盖」。**证书只存路径，不存内容**：私钥一旦进库，`GET /api/preferences` 会把整行原样返回（Web 形态下那是给任何持有 bearer 口令的客户端看的），SQLite 文件本身也是一份用户没预期的备份。路径由**运行请求的那台机器**解析：桌面端是本机路径，`serve-web` / Docker 端是服务端容器里的路径。

**PEM 的区块边界必须补齐，否则 `reqwest` 会整段跳过后面的区块。** `reqwest` 的 PEM 解析器按行读区块：某个区块的 `-----END …-----` 后面若没有换行，下一个区块的 `-----BEGIN …-----` 就与它粘在同一行里，解析器把整行当成前一个区块的结尾，于是**后面那个区块被整段跳过**。实测：把「证书.pem」与「私钥.pem」直接首尾相接时，私钥那份读不到，报错是「private key or certificate not found」——而 PEM 本身完全合法。「证书与私钥分两个文件」正是最常见的 mTLS 材料形态，且用户给的文件末尾常常没有换行，故 `core::tls::normalise_pem_boundaries` 在读进来之后先把每个 END 标记后面的换行补上。改这块时不要绕过它。

**`reqwest` 的 TLS 后端是 `rustls-tls`，不是 native-tls。** 两个后果：`danger_accept_invalid_certs` 与 `danger_accept_invalid_hostnames` 要**一起**开（只开主机名那一个会落到另一个分支：证书链照查、主机名不查，与「跳过校验」不是一回事）；而 `danger_accept_invalid_certs` 打开时 rustls 后端会整体换掉证书校验器，信任链（含加进去的自定义 CA）根本不参与，故「跳过校验」与「挂 CA」不必同时开。

**自定义 CA 是**追加**到内置根证书集，不是替换它。** `add_root_certificate` 只是把证书推进 `config.root_certs`，而 reqwest 在 `build()` 时把 `webpki_roots::TLS_SERVER_ROOTS` 一起 extend 进同一个 root store —— 本仓库从未调 `tls_built_in_root_certs(false)`。故「只信任这张 CA」是**错的说法**：内置的公共根证书集照样有效，界面与文档都要写「额外信任」。另一层：这套客户端用的是 reqwest **内置的 Mozilla 根证书列表**（工作区 `Cargo.toml` 里 `reqwest` 开着 `rustls-tls`），**本机证书库不参与** —— 把公司根证书装进 Windows 证书库不会让它被信任。

**证书路径字段要在写入口校验，否则「只存路径」会被用户手滑破掉。** 类型层面挡住了应用自己写证书内容（那几个字段只有路径），但挡不住用户把私钥正文**粘进**路径输入框 —— 那段文本会原样落进 `preferences` 的 `request_settings` 行或 `endpoint_details.tls_json`，而 `GET /api/preferences` 把整行原样返回。故 `TlsSettings::validate()` 拒绝含 `-----BEGIN` / `-----END` 或换行的值。**校验放在写入口，不放在类型上**：`request_settings` 那一行有三条写路径（桌面端的专用命令、`PUT /api/request-settings`、`PUT /api/preferences` 这个通用入口），故 `db::preferences::set` 在键是 `request_settings` 时调它 —— 放在通用写入口，三条路径才都拦得住；`db::endpoint_details::{create,update}` 各调一次。

**那道校验不能被「解析失败」绕过去。** `db::preferences::set` 若写成 `if let Ok(settings) = serde_json::from_str::<RequestSettings>(&raw)`，反序列化失败时 `if let Ok` 不匹配，校验整段被跳过，写入照旧执行 —— 而失败的原因（`timeoutMs` 的类型写错）与要防的东西（同一个请求体里 `tls.clientKeyPath` 粘着私钥正文）可以出现在同一个 JSON 里。故 `request_settings` 这一行**读不出 `RequestSettings` 就是形状不对，要报错**，不得照旧存下去。同一条：这一行**存重新序列化后的那份**，不存请求体原样 —— 域类型不收陌生键，原样存会把调用方塞进来的陌生键连同其中的证书正文留在这一行里，而 `GET /api/preferences` 把整行原样返回。

**地址是每个 (环境 × 模块) 一格，每格装模块地址与路径前缀改写规则。** 没有项目级的地址表，环境与模块之间也没有第二个键：`environments.module_base_urls_json` 是 `module_id → { url, rewrites }`，其中 `rewrites` 是**有序**的路径前缀改写列表（按顺序匹配、命中首条即停止），各格互不相干；旧行的单条 `rewrite` 由 `ModuleBaseUrl` 的反序列化提升成单元素列表，故 `SCHEMA_VERSION` 不动。模块没有格就是没有地址，**什么都不继承** —— 连别的模块的也不沾，这一层之上刻意没有回退。解析器是 `resolve_base_url`（`crates/simple-post-mcp/src/variable_fill/base_url.rs`），改写本身住在 `simple_post_core::url::apply_rewrites`（MCP 侧与导入导出侧都调它，故 Rust 只有一份实现）；端点自己的 `baseUrlOverride` 短路的是*地址*（改写规则照样生效 —— 它改的是端点自己的路径，主机与它无关），而一格只带改写规则、没有地址时，解析结果是「没有地址」而不是那条规则。

**Request scripts live in `simple-post-core::script`, and the whole sequence is written once.** A user's JavaScript runs in an embedded QuickJS sandbox (`crates/simple-post-core/src/script/`): the only host capabilities are what one fixed JS prelude hands over (`pm.request` / `pm.environment` / `pm.response` / `pm.test` / `pm.expect` / `console.log`), so "the script cannot reach the filesystem, the network or a process" holds because that path does not exist rather than because each one was disabled. The sequence — assemble the chain → pre-request script → send → test script → write environment variables back — is implemented **once**, in `script::send_with_scripts`; the desktop path (`http_request` / `POST /api/http/send`) and MCP (`api_call_endpoint`) both call it. If you move a step, change it there: a second ordering, written in the frontend or in the MCP handler, is exactly the drift this design exists to prevent.

The chain order is **collection → nested collection → endpoint**, and the pre-request and test phases use the *same* order (Postman's own documentation says so). Do not reverse the test phase — some third-party write-ups claim it runs endpoint-first, and they contradict the upstream docs. Each script is atomic: if it throws or is interrupted, its changes to the request **and to the environment / request-scoped variables** are discarded while its logs and assertions are kept — the chain shares one sandbox, so a leaked value would otherwise be readable by the next script and persisted by it.

**The send carries the scripts that are effective *right now*, not the stored ones.** The renderer sends the endpoint's own `preRequestScript` / `testScript` (the draft first, falling back to the stored value) and the backend overrides the stored ones with them, field by field (a field the payload does not mention keeps the stored value). Otherwise a script the user edited but has not saved yet would not run — the preview and the actual request would describe two different things. The endpoint id is still sent, and it is what assembles the *collection* chain; a draft endpoint has no row, hence no collection chain, but its own two scripts still run.

Two more rules the sequence obeys: the **test phase sees the pre-request phase's environment writes** (Postman lets a pre-request script hand a token to the test script), and a **failed environment write-back does not fail the send** — the request has already happened and the script outcomes are in hand, so the failure is recorded as a script error instead of replacing the response.

**The script sandbox inherits that discipline, and it is enforced by a test.** `simple-post-core::script` is linked into the MCP daemon, so a `println!` in it corrupts an AI client's stream. `console.log` from a user script goes into an in-memory array (`stdout_test.rs` scans the module's sources for `println!` / `print!` / `dbg!` and fails the build). Two more rules for the same module: **no panics** — the release profile is `panic = "abort"`, so a panic in the script path takes the whole process down — and **the engine's memory limit only works with the default allocator**, so the `rust-alloc` / `allocator` features of `rquickjs` must stay off (with a custom allocator `set_memory_limit` is a silent no-op, and the memory ceiling this project promises would be a lie). The interrupt handler is what makes a timeout real: it returns `true` and the engine raises an *uncatchable* exception, so an endless loop is interrupted rather than waited out. The script phase runs inside `spawn_blocking` — the engine is synchronous and CPU-bound, and running it on an async worker stalls the runtime.
