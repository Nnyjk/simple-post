# 渲染层

> 从 `AGENTS.md` 拆出的按需文档，原文逐字保留。只有动到本域时才需要读它。

**树行是三块 —— 前导槽、名称框，以及尾部那个「新建」按钮 —— 它的两种交互彼此分开。** `rows/TreeRow.tsx` 把箭头渲染成自己的 `<button>`（`data-testid="tree-toggle-btn"`、`aria-expanded`），放在行标签按钮旁边而不是里面：按钮套按钮是非法 HTML，浏览器随后会把两次点击并成一次。`useTreeSelection` 据此把动作拆开：`openModuleTab` / `openCollectionTab` 只调 `openTab`，别的什么都不做；`toggleExpanded` 调 `toggleNodeExpanded`，箭头调的就是它。箭头**不**发起拖拽（没有 `draggable`、没有 `onDragStart`）：它是展开控件，能拖会让人以为整行可以被拖走。它仍然接收放置，因为把节点放到箭头这一条上，与放到行名上是同一个动作。箭头与名称框在静止态都没有边框和阴影：两块各自把边框画在一层透明覆盖层上，指针进入哪一块，GSAP 就把那一块淡入、离开时淡出。故指针没进入任何一块之前，一行显示的就是树背景上的纯文本。放箭头的那个前导槽（`SLOT_W`，16px）只比图标宽一点，箭头因此紧贴名字。箭头与名称框的高度取自同一个常量（`BLOCK_H`），图标与文字才在同一条线上；名字在框内左对齐，方法胶囊（接口行）放在那个框**里面**、名字前面，胶囊与名字算一个整体。箭头与名称框相距 2px（行容器的 `gap-0.5`）。接口行没有箭头，但在左侧留一个同样宽的空槽；`rows/EndpointList.tsx` 不再给接口行加缩进 —— 接口的名称框因此与它父级的名称框落在同一条竖线上。`src/features/project-tree/__tests__/tree-toggle-split.test.ts` 钉住这套接线。

**两个界面，按 `activeProjectId === ''` 切**（`src/App.tsx`）。`WelcomeScreen` 是整窗页面，没有顶栏、没有树、没有标签条；其余一切住在 `WorkspaceShell`（`src/features/workspace/`），它是 `lazy()`。这个切分一次做成三件事：把整个工作区 —— 以及经由它进来的 CodeMirror 编辑器 —— 挡在冷启动 chunk 之外；与下面那套两层 `bootstrap()` 配对；让「没有项目」的状态真的空着，而不是一屏什么也干不了的控件。`leaveProject()`（顶栏那个字标）是回去的路。

**设置是第三个宿主，不是第三份实现。** 设置这个单例本身也是一个*标签*，故它必须在没有项目时也能打开 —— 否则欢迎页上的「打开设置」只会写一个没人渲染的标签，看着像什么都没发生。`App.tsx` 因此多一个分支：`activeProjectId === '' && activeTabId === SETTINGS_TAB_ID` → `SettingsSurface`（`src/features/settings/SettingsSurface.tsx`）。这个 `lazy()` 的整窗宿主只补一个独立界面需要的框（拖拽区、返回、窗口按钮），里面装的**就是**工作区当标签挂的那块 `SettingsPanel`。两个宿主、一块面板：每个小节从 store 读而不吃 props，两边因此不会各说一套。`SettingsPanel` 按 `activeProjectId !== ''` 判环境小节的可用性 —— 没有项目时点「新建环境」会往 `projectId === ''` 写并静默失败，所以那里渲染一句提示。两个宿主都是 `lazy()`，`SettingsPanel` 是共享 chunk：不要从 `App.tsx` 静态 import 任何一个。

**两层 `bootstrap()`**（`src/stores/bootstrap-slice.ts`）。第一层是 `projects_list` + `request_settings_get`，await 等它；它翻真 `loaded`，HTML 启动画面随之撤掉。第二层是 `nodes_list` + `endpoint_details_list` + `environments_list`，由 `loadWorkspace()` 跑，**不** await。由此有三条后果：`nodesLoaded === false` 时 `nodes: []` 是歧义的（渲染加载态，别说「该项目还没有模块」）；第二层的失败落进 `nodesError` 而不是 `bootstrapError`，故一次树加载失败不会把启动画面卡住；`pruneStaleTabs()` 在 `nodesLoaded` 之前不动作，否则它会删掉每一个它本该留着的标签。请求设置搭在第一层里，是因为设置面板从欢迎页就打得开 —— 谁打开它之前，那几个旋钮得已经就位。

**刷新后回到上次停留的项目，而不是回到欢迎页.** 「我在哪个项目里干活」是渲染层的会话事实，故它存在 localStorage 的 `simple-post:prefs` 里（`ui-prefs.ts::readLastProjectId` / `saveLastProjectId`），与主题同一份偏好。**记住它由 store 的订阅负责**（`app-store.ts` 订阅 `activeProjectId` 的变化）—— `activeProjectId` 有三条改法（`openProject` / `setActiveProject`，命令面板跨项目跳接口走的是后者；`deleteProject` 删掉在前面的项目时把用户送到幸存的那个），在各动作里分别写必然漏掉一条，漏掉的后果是记住的项目与实际所在的项目脱节。订阅还顺带把**回滚**算进去：`deleteProject` 失败时 `set(snapshot)` 把 `activeProjectId` 改回去，记住的值跟着回滚；写在乐观 `set()` 里则做不到。`bootstrap()` 在第一层落地后据此进入那个项目 —— 项目已不存在时清掉那条记录并留在欢迎页（这一处要自己写：`activeProjectId` 没变，订阅不会替我们做）。**恢复发生在 `loaded` 翻真之前**：`App.tsx` 按 `activeProjectId` 选界面，晚一步就会先画一帧欢迎页再被换成工作区。两处陷阱：`setTheme` 必须**合并**进那份偏好（整份替换会把记住的项目抹掉，于是换一次主题就把刷新后的落点退回欢迎页；同一份偏好里还放着「每个项目上次用的环境」，故它一并被抹掉）；设置标签不参与恢复——项目里打开设置后刷新回到**项目**，欢迎页里打开设置后刷新回到**欢迎页**。

**偏好键与主题解析只有一处定义。** `simple-post:prefs` 这个键与「什么算合法主题」的判断写在 `src/lib/theme-boot/index.ts`。三处从它派生：`index.html` 的 `<head>` 里那段同步脚本由 `vite.config.ts` 的 `themeBootPlugin` 在**构建期**从这份源码生成（内联脚本是 classic script，浏览器不允许它 import 模块，故插件把唯一的默认导出改写成全局赋值，共享模块因此必须运行时零依赖）；store 的初值与「记住上次停留的项目」也从它读。**校验不能省**：存下来的主题必须过 `resolveTheme`，非法值回落到 `dark` —— 少了这一步，store 会把非法值当主题存下，而 `useIsDark` 只认 `dark` 与 `light`、其余按「跟系统」处理，于是首帧画深色、随后 React 画系统色。

**变量提示只覆盖会被替换的取值栏，工具是共用的一份.** 提示工具在 `src/features/http-tester/var-hint/` 下，URL 栏、query 参数值栏、请求头值栏、鉴权值栏与请求体编辑器共用它。**给提示的字段只有那些上线前会被 `{{var}}` 替换的**：query 参数值、请求头值、请求体的内容、鉴权的 token / 账号 / 密码 / API Key 的**值**，以及 OAuth2 的 **token 端点 / 授权端点 / client id / scope** 那四个字段（它们由后端在取 token 之前替换，字段清单见 `src/lib/http-build/auth.ts::OAUTH2_SUBSTITUTED_FIELDS`）。名称类字段（参数名、请求头名、API Key 的名）与 OAuth2 的 **clientSecret / password / authCode** 不给提示 —— 它们不参与替换，给了只会把用户引到错的字段上。候选列表只算一次（`model/varEntries.ts::buildVarEntries`，动态变量在前、环境变量在后），经 `TesterShell` 显式下传，不走 Context。

界面上「当前环境」只写 store，不发 IPC（`bootstrap-slice.ts::setCurrentEnvironment`）。它按项目记在本机 localStorage 的 `simple-post:prefs` 的 `currentEnvByProject` 字段里，**记住这件事由 store 的订阅负责**（见 `app-store.ts`）：`activeEnvironmentId` 有好几条改法（切换项目、切换环境、删除环境、删除项目、重新加载工作区），在各动作里分别写必然漏掉一条，漏掉的后果是记住的环境与实际所在的环境脱节。**每条改法都要让 `activeEnvironmentId` 落在新项目的环境上**：删除当前项目时用户被送到幸存的那个项目，而 `activeEnvironmentId` 若还指着已删项目的环境，订阅就会把那个悬空 id 写进幸存项目的记忆里，把幸存项目自己记住的环境顶掉。

**设置面板里的环境条跟着当前环境走.** 那一栏改的是「这个环境在各模块下的地址与变量」，而请求发出去时用的也是当前环境 —— 两者停在不同的环境上，用户改的是一处、跑的是另一处。故 `EnvironmentSection` 与 `ModuleBaseUrlSection` 打开时选中**当前环境**（它不属于本项目时才退回默认环境），而不是无条件退回默认环境。用户在这条环境条上明确选过哪一枚之后就不再被拽走。

**开发服务器不做启动调优，这是有意的。** 早先有一块 `optimizeDeps.noDiscovery` + 短 `include`，守着一个实测的 **11.3 s → 139 ms** 冷启动首请求，看着像地雷。Vite 8 下它已经失效：带那块时欢迎页的模块图是 **9,622 KB / 43 modules**，不带是 **9,570 KB / 43 modules** —— 配置仍会缩小依赖*优化器*要干的活（预打包 10 个依赖而不是 27 个），但那份工作不在首屏路径上，浏览器实际拉取的字节没变。故它被删掉，而不是作为一条假约束留着。别再加回来，也别把「优化启动」当成这里的待办。

**服务端发出的字节不等于用户感知的开发速度。** Vite 8 下同一张欢迎页模块图从 3.2 MB 变成 9.6 MB（两边都是 43 modules），那块 `optimizeDeps` 既没造成也没治好它 —— 而 `npm run dev` 在编译与加载两头都实测更快。这里的字节是带宽事实，不是延迟的代理，故别为了把它们压回去去找配置。真要量一次打包改动：`GET /` 量不到东西，它返回 `index.html`、根本碰不到依赖优化器；跟 `import()` 量的是「把一切加载完」而不是首屏时间。有效的探针要从入口爬**静态** import 图，跨改动比模块数与字节。

**`manualChunks` 必须保持函数形态。** Vite 8 跑在 Rolldown 上，兼容层会自动转换大部分 `rollupOptions` —— 但**不**含对象形态的 `manualChunks`。`manualChunks: { react: [...] }` 直接构建失败，报 `Expected Function but received Object` / `manualChunks is not a function`；只有 `manualChunks(id) { ... }` 能跑。对象转函数是机械替换，但背后的意图不是：CodeMirror 与 `marked` 必须留在每一个静态入口之外 —— `manualChunks` 会把列出的模块连同依赖闭包提进一个 chunk，Rollup/Rolldown 随后为它发一条**静态** import，那正是编辑器改成 `lazy()` 之前 425 kB 编辑器压上关键路径的原因。验证办法是读 `dist/assets` 里产出的 chunk 图、grep 入口的静态 import：只看 chunk **清单**看不出静态 import 边。Vite 8 下这张图是干净的 —— 首屏静态图 **5 chunks / ~323 kB raw**，其中没有一个能到达 CodeMirror 或 `marked`（v0.1.30 实测：entry 99.5 kB + react 218.8 kB + 三个小 chunk）。**入口 chunk 自身的体积不是稳定值**：加一个模块可能让 Rolldown 把某个共享 chunk 内联进去（脚本编辑器落地时一个 23 kB 的 `utils` chunk 并进了入口，入口从 59 kB 长到 80 kB，整张图仍是 298 kB）。那只是把字节在文件之间挪动，没挪出关键路径，故要量整张静态图而不是入口文件 —— 也不要靠「钉住 chunk」去「修」它。

**GSAP 不在关键路径上。** `src/lib/gsap.ts` 拉进 core + CSSPlugin（~60 kB raw），故从入口 chunk 能到达它的任何东西都要在每次冷启动时付这份钱。这就是 `WelcomeScreen` 的入场用 CSS（`globals.css` 里的 `.welcome-enter`）而不是 `gsap.from()` 的原因，也是 `CreateProjectDialog` / `BootstrapErrorBanner` 挂在 `newItem.open` / `bootstrapError` 上而不是无条件渲染的原因 —— `lazy()` 组件只要被*渲染*就发起 import，故只套一层 `<Suspense>` 照样会在首屏把它下载下来。验证走 **Vite `manualChunks`** 那条里写的依赖边探针；只看 chunk 清单看不出静态 import 边。

**Zustand 的服务端快照是**初始状态**，故 `renderToStaticMarkup` 渲染不出改过的 store.** `useStore` 把 `api.getInitialState()` 当作 React 的 `getServerSnapshot` 交给 `useSyncExternalStore`，于是服务端渲染读到的永远是 store **创建时**那份状态，测试里那句 `useAppStore.setState(...)` 改不动它 —— 用例却会「看起来跑了」。要在服务端渲染里覆盖某个状态，有两条路：把那段渲染提成**收 props 的组件**（如 `TlsPanel` 那样），或者把判断提成**纯函数**（如 `isRequestSettingsDirty` 那样）。**别把 `setState` 之后的结果当成已渲染的内容去断言。**

**One modal layer, one set of layers.** `src/components/ui/modal-surface.tsx` is the only implementation of "modal": portal, Esc, backdrop click, focus trap, background `inert` + `aria-hidden`, entrance animation. The page itself never scrolls: `globals.css` sets `overflow: hidden` on `html, body, #root`, so the surface does not lock scrolling in JavaScript. `Dialog` (title / description / body / footer) and `CommandPalette` (search row / result list / shortcut hints) are the two surfaces built on it — they differ in *shape*, not in modal semantics, so a third one must reuse `ModalSurface` instead of hand-rolling another full-viewport overlay. Esc is handled **once**, in `ModalSurface`'s capture-phase listener, which `stopPropagation()`s so React's `onKeyDown` never sees it; a second handler would close the surface twice or fight the first. `ModalSurface` keeps a module-level stack of the open surfaces and closes a surface only when that surface is the top of the stack: without the stack, two open surfaces would both answer one Esc and the lower dialog would close along with the upper one. The background's `inert` is **counted**, not toggled — the background stays inert until the last surface closes, so closing the upper one does not unlock the background while a dialog is still open. The background is `inert` while a surface is open, which is what makes "背景点不到、Tab 进不去、读屏读不到" true, and it is also why focus returns to the trigger on close — the restore happens **after** the `inert` is lifted, because an element that is still inert refuses focus. A surface records `document.activeElement` **during render**, before the panel mounts: by the time an effect runs, the browser has already moved the focus onto the panel's own `autoFocus` element, and that element disappears with the panel, so the recorded element would never receive the focus back. Floating layers take their `z-index` from `src/components/ui/layers.ts` (`popover` 50 / `contextMenu` 60 / `tooltip` 70 / `modal` 100 / `tooltipInModal` 110): a literal `z-…` written into a component makes the ordering unknowable. A tooltip inside a modal needs `tooltipInModal`, because the modal panel covers the `tooltip` layer; `Tooltip` picks the layer by asking whether its trigger sits inside `[data-modal-surface]`. The one such tooltip today is the "已存在" badge in the import preview.

**JSON 的键值树、右键菜单与悬浮工具条各只有一份实现，三处用途共用它。** `src/components/ui/json-tree-view.tsx` 是那棵可折叠的键值树：响应体的 Pretty 页与请求体的 json 载荷「树」档都渲染它，故它只认 `text` 与 `wrap` 两个 prop —— 不读 store、不认识 endpoint，也不接 `onChange`。**树只读，写回只发生在 Raw 档**：载荷一旦有两个写入口，树里点到的那一份与编辑器里那一份会互相覆盖。树的模型（路径、预览、子树 JSON、摊平顺序）全在 `src/lib/json-tree.ts` 的纯函数里，由 `src/lib/__tests__/json-tree.test.ts` 直接断言 —— runner 没有 DOM，渲染结果只能靠源码哨兵（`response-viewer-dual-view.test.ts` / `body-json-view.test.ts`）钉接线。两条与浏览器行为有关的规矩：**行不是按钮**（行没有点击行为，做成按钮会给 22 行各塞一个空的 Tab 停点，按钮里的文本还选不中，`select-text` 才是它的职责），箭头才是 `<button>`；**右键菜单挂在行容器上**，条目只认那一行的节点。`src/components/ui/float-toolbar.tsx` 是那排浮在内容右上角的小图标按钮（复制、自动换行、Raw 档的格式化），它只负责定位与提示，语义全在 `actions` 里。**它的实际高度是 42px（`top-2` 8 + 边框与 `p-0.5` 与 `h-7` 合计 34），宿主必须让出这一条**：`PrettyView` 的外层因此是 `pt-11` 而树自己只剩 `pt-1` —— 让位只能有一处，两处各让一次会把首行推得太远，一处不让则长行从按钮底下穿过去。`src/components/ui/context-menu.tsx` 是唯一的右键菜单实现（portal、视口收拢、Esc、屏蔽原生菜单、`LAYER.contextMenu`），`features/project-tree/TreeContextMenu.tsx` 只是它的转发壳 —— 新加一个右键菜单要复用它，不要再写一份浮层。

**`reloadWorkspace` vs `loadWorkspace`.** The second layer is idempotent (`nodesLoaded` / in-flight guard) so `bootstrap`, `openProject` and the retry button can each call it uncoordinated. An import writes dozens of rows in one transaction and gets back only ids, so refreshing with the idempotent one silently leaves the tree stale. Use `reloadWorkspace` there; do not remove the guard from `loadWorkspace` to "fix" it, or a tree failure strands the boot splash.

**One thing a whole-array replacement must not flatten.** `expanded` lives only in the renderer (the server never stores it), so `reloadWorkspace` has to merge each node's old `expanded` back in **by id** — a plain replacement collapses every branch the user had open (#74).

**IME guard.** Global shortcuts in `src/App.tsx` must check `e.isComposing`, else CJK IME Enter fires requests.

**The tab strip's active-indicator is derived per frame, never measured once.** `WorkspaceTabs.tsx` keeps one persistent bar at strip level and, while anything that can move a tab may be animating, re-reads the active tab's *live* rect every animation frame and eases toward it (`BAR_APPROACH` / `BAR_SETTLE_MS`). Do not "simplify" this back to `offsetLeft` + `gsap.to`. Two things move those tabs and both can be mid-flight at the moment a one-shot measurement is taken: the Flip tween (with `absolute: true` every tweened tab reports its **pre-commit** position) and the strip's `scrollLeft`. Measuring once is what produced the bar drifting to the wrong x and keeping a stale width when tabs were closed. The bar's x is in **content** coordinates — add `strip.scrollLeft` back, or it drifts by exactly the amount scrolled.

**标签条不收缩：放不下就横向滚动，位置与滚动仍由同一条 GSAP 通道负责。** 标签恒为 `w-[160px]`，没有 compact 档，故宽度不参与任何动画——Flip 只补间位置，激活指示条的宽度每帧直接取激活标签的宽度。标签多到放不下时条横向滚动，底部给一条 3px 的**覆盖式**滚动条（`absolute`，不占布局、不改标签高度，激活标签与下方面板的底边贴合因此不变），几何由 `src/features/workspace/tab-scroll.ts::scrollbarThumb` 算出、滑块可拖动；尾部「关闭其他标签」按钮在滚动区**之外**（外层容器里），故它既不随内容滚走，也不占滚动区的 `clientWidth`。九条规矩：上一次补间在下一轮开始前 `progress(1)` 落定，**落定时不能加 `suppressEvents`**——那会把 GSAP 还原标签样式的回调一起抑制掉，标签就此停在绝对定位上，条的内容宽度从此算不对；标签上不得有宽度的 CSS 过渡；横向滚动不得用原生 `scrollIntoView`，该滚到哪儿由 `src/features/workspace/tab-scroll.ts` 算出、滚动本身交给 GSAP 补间；**条滚动之后必须重新记录布局**——Flip 记的是视口坐标，`scrollLeft` 一变那份记录就过期了，下一次增删标签时 Flip 会从过期的视口坐标起步，整条标签先横跳一截再滑回正确位置（程序滚动在补间结束时重记，滚轮滚动在停下来后重记，补间进行中不记——那时量到的是动画中途的位置）；**本次新出现的标签必须并进那份记录**——Flip 会把不在记录里的标签当成进入元素，让它留在文档流里，其余标签被移出文档流之后它就退回条的最左边，与第一个标签重叠。滚动补间只在该滚的时候存在：目标已在可视范围时、滚轮接手时都要先 `killTweensOf` 停掉它，否则条会继续往旧标签那边滑，把刚点开的标签带出视野；Flip 补间还在跑时也不要立刻滚，那一刻标签的位置是动画中途的位置，算出来的滚动目标是错的。**横向手势也算滚动**——滚轮取主导轴（`|deltaX| > |deltaY|` 时用 `deltaX`），`overflow-hidden` 关掉了原生滚动，只认 `deltaY` 时触控板的横滑什么都不发生；**监听器跟着节点走**——条在最后一个标签关闭时整条卸载、下一条标签出现时重新挂载，故滚动区节点进 state（`stripEl` ＋ 回调 ref `attachStrip`），副作用依赖它才会在重挂后重新挂上监听。回归网是 `src/features/workspace/__tests__/tab-strip-animation.test.ts`（源码哨兵）与 `src/features/workspace/__tests__/tab-scroll.test.ts`（滚动目标的纯单测）。

**标签条的批量关闭有三条约定.** 其一是**基准标签**：右键菜单的「关闭其他」以**被右键的那个标签**为基准，不是活动标签 —— 标签条末尾那个「关闭其他标签」按钮走同一条路径但不传基准（保留活动标签），两条路径不能互相覆盖。其二是**关掉提示栏等于取消**：`DirtyCloseDialog` 的标题行 × 与 Esc 走 `resolveDirtyClose('cancel')`，一个标签都不关、未保存的修改原样留着 —— 用户既然关掉了对话框，就是改了主意，顺手把他的标签关掉不是他表达的意思；「直接关闭」按钮仍是丢弃并关闭。四个批量动作（关闭其他 / 关闭左侧 / 关闭右侧 / 关闭所有）共用 `dirty-tabs-slice.ts` 里那一份 `closeWithDirtyGuard`，脏的那部分排进队列、干净的立刻关掉。回归网是 `src/stores/__tests__/tab-close-actions.test.ts`。其三是**动态变量标签的脏来自它那份草稿**：`dynamic-slice` 在草稿出现时把 `dynamicTabId(projectId)` 推进 `dirtyTabIds`、在草稿清掉或标签关掉时摘掉，故「关闭已保存」不会带走用户填了一半的表单——这条不靠 `closeSavedTabs` 放宽过滤，靠的是脏标记本身准确。同一条「只减不重建」也适用于 `endpointDrafts` 与 `draftEndpoints`，四个动作一个形状：`pruneStaleTabs` 从现有表里删掉 `removedIds`，`closeAllTabs` 与 `closeSavedTabs` 从两者删掉被关掉的那些 id（`withoutTabKeys`），都不按可见标签重建——暂存进 `projectTabs` 的标签不在 `openTabs` 里，重建会把它的草稿与文档一起抹掉，而它那条脏标记还留着，于是出现「脏而无草稿」。注意「脏标记决定关不关」那条判据不动：暂存标签若真有草稿，它本来就该是脏的。

**Semantic token pairing — a `-foreground` token is a colour for text *on* the saturated fill, not on a surface.** `--destructive-foreground` exists to sit on the solid `--destructive` fill, and it **swaps polarity** between scopes: `0 0% 100%` (white) in light, `0 0% 10%` (near-black) in dark, because `--destructive` itself swaps with it (`5 59% 44%` dark red ↔ `354 100% 80%` light pink). Pairing it with a *tint* of that fill therefore breaks one scope: `bg-destructive/10 text-destructive-foreground` is white-on-pale-pink in light mode and merely acceptable in dark. Two correct shapes: **solid** `bg-destructive text-destructive-foreground` (both tokens together, ~4.8:1, nothing overrides either), or a tinted surface with `--destructive` as the text — it is the only token that lightens in the dark scope, so it reads on a 5–10% tint in both. `success` / `warning` are the opposite case: their `-foreground` **is** the text tier (30% light / 75% dark) and the base value only reads as a border, which is why those badges use `bg-success/15 text-success-foreground`. `<InlineError>` (`src/components/ui/inline-error.tsx`) and `IconTile`'s `danger` tone both carry the second shape; copy either, not the pairing.
