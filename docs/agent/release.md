# CI、发布与更新

> 从 `AGENTS.md` 拆出的按需文档，原文逐字保留。只有动到本域时才需要读它。

**CI quality gate** — `.github/workflows/ci.yml`, on every push to `main`, every PR and manual dispatch:

- `Web — format, lint, typecheck, test, build` (ubuntu, Node 22): `format:check` → `lint` → `typecheck` → `npm test` → `lint:openapi` → `vite build`
- `Rust — fmt, clippy, test` (windows-latest): `cargo fmt --check` → `clippy -D warnings` → `cargo test --workspace`. `swatinem/rust-cache` runs with `cache-target: true`, because three separate cargo invocations each cold-compiling the same `target/` was the expensive half.
- `Docker — image build + container smoke test` (ubuntu, 75 min budget): builds `linux/amd64`, then runs a **running-container** smoke test — HEALTHCHECK wait, `/healthz` body assertion, SPA shell + hashed asset fetch, unauthenticated `/api/*` → 401, project create over REST, `id -u == 10001`, no `libgtk`/`libwebkit`, and a *replaced* container against the same named volume.

Those three display names are the **required status checks** configured on `main` (see #25). Renaming a job is therefore a settings change, not just a YAML edit.

`web` and `rust` are unconditional — measured at 37s and 1m57s, they cost nothing to always run, and keeping them unconditional is what makes "a skipped required check means passed" safe. `docker` measures 185s (158s image build + 13s smoke) and runs in parallel with `rust`, so it no longer sets a run's wall clock. `docker` alone is scope-gated by a `changes` job using `dorny/paths-filter` because a README-only PR changes no byte of its work, so it is skipped. Its `if` is `!cancelled() && outputs.docker != 'false'` — the fail-closed half, so a broken filter runs the gate instead of reporting green. A skipped job is reported successful, which is why a skipped required check is acceptable.

Publishing: `release.yml` (desktop installers, draft) and `publish-image.yml` (GHCR, `linux/amd64`) both trigger on `v*`. Both use `cancel-in-progress: false` — cancelling a publish halfway leaves a partial release, which is worse than the duplicate it prevents.

**`npm run release` is the whole release; `main` is protected, so the release commit enters through a PR.** `node scripts/release.mjs patch|<x.y.z>` (default `patch`: `0.1.39` → `0.1.40`) rewrites the four version sources, refreshes both lockfiles, lands the bump through a PR and tags the merge commit. **The project stays on `0.1.x` for a long time and only the last segment is incremented, without a ceiling**: `0.1.99` → `0.1.100` → `0.1.101` → … — there is no "save up for `0.2.0`", so `minor` / `major` are not inputs at all (`resolveNextVersion` rejects them and says why); an explicit `x.y.z` is only an escape hatch for a tag that was cut wrong, and must be strictly greater than the current version. Note that `npm run release --dry-run` does **not** work the way it looks: npm eats `--dry-run` / `--publish` as its own config keys, so the script folds `npm_config_dry_run` / `npm_config_publish` back into its argv and warns — write `npm run release -- --dry-run`. A direct `git push origin main` is rejected by the branch protection hook with `Changes must be made through a pull request`, and `enforce_admins` is on, so an admin token does not get around it. The release bump therefore lands the way v0.1.22 did: a branch named `chore/release-<version>` carries the `chore(release): <version>` commit, a PR opens against `main`, and the PR merges with **rebase merge** — rebase keeps the commit body verbatim, while squash would replace it with the PR title. Four version sources move together and none may be skipped: `package.json`, the `[workspace.package]` block of the root `Cargo.toml`, `src-tauri/tauri.conf.json`, and the README badge. `Cargo.lock` and `package-lock.json` follow from `cargo metadata` and `npm install --package-lock-only`, and should carry nothing but the version lines — the script refuses to commit when `git diff --name-only HEAD` lists a seventh file or when a lockfile's `git diff -U0` hunk mentions neither version (`git diff --stat` is only printed), so an incidental dependency re-resolve fails the release instead of riding along. The tag is `v<version>`, annotated, pushed after the merge: `git tag -a v0.1.40 <merge commit> -m "Simple Post v0.1.40"`.

**The release notes are generated from the commit titles, and the draft may only go live after `fix-updater-json` succeeded.** Nobody writes the `### 这一版的改动` section any more: `scripts/release-core.mjs` turns `git log --oneline v<previous>..v<new>` into `### 新功能` / `### 修复` / `### 重构` / `### 性能` / `### 测试与构建` / `### 其它` (empty groups are dropped, `chore(release)` and merge commits are skipped) — one release every few days makes a hand-written summary cost more than it says. `release.yml` writes the install instructions plus that placeholder into the body and leaves the release as a **draft**; the generated section is merged into that body (`scripts/release-core.mjs`: `mergeReleaseBody`) and written back with `gh release edit <tag> --notes-file <file>`, which only adds `--draft=false` once the pipeline is safe to publish. Safe means **every job of the run, not just the three matrix builds**: the trailing `fix-updater-json` job rewrites each `latest.json` platform URL from `https://api.github.com/repos/…/releases/assets/<id>` (an API endpoint that answers `403` to the updater's request, which sends no `User-Agent`) to the public `browser_download_url`. Publishing before it finishes ships an update every installed client fails to download — that is exactly how 0.1.35 → 0.1.36 broke. So `--publish` polls `gh run view <id> --json status,conclusion,jobs` until the whole run is completed and green, aborts naming the failed jobs, and additionally asserts that a job *named* `fix-updater-json` succeeded (the run stays green if someone drops that `needs:`). Without `--publish` the script stops at the tag: it prints `gh run list --workflow=release.yml` to watch the run and, once the whole run (including `fix-updater-json`) is green, `npm run release -- --notes <tag>` to finish. `--notes <tag>` is a **separate later step**, not part of the main flow, because the draft only appears 20–40 minutes in, when `tauri-action` uploads the matrix builds — polling for it inside the main flow reports "the pipeline just started" as a failure. It resolves the previous tag from `git tag --list 'v*' --sort=-v:refname` rather than `package.json` (by then the repo already says the *new* version), collects the `v<previous>..v<tag>` commit titles, polls the draft body, merges through `mergeReleaseBody`, writes `release-notes-<version>.md` in the repo root and prints the `gh release edit <tag> --notes-file <file> --draft=false` that publishes it. Both `--notes` and `--dry-run` go **after `--`** (`npm run release -- --notes v0.1.40`): npm otherwise swallows the flag as one of its own config keys — harmless for `--dry-run`, which the script folds back with a warning, but for `--notes` the tag value lands in the positional slot, i.e. reads as an explicit version, i.e. ships a release; the `npm_config_notes` guard exists to refuse exactly that. The tag must be **annotated** — `git tag -a v<version> <commit> -m "Simple Post v<version>"`; a lightweight tag loses the version string from the tag list. `publish-image.yml` pushes four tags for the same build: `0.1.23`, `v0.1.23`, `0.1` and `latest`; each must resolve to `linux/amd64`. The `gh` token does not carry `read:packages`, so the tags are verified through the registry's own API instead: fetch an anonymous token from `https://ghcr.io/token?scope=repository:nnyjk/simple-post:pull&service=ghcr.io`, then list `https://ghcr.io/v2/nnyjk/simple-post/tags/list` with it. **A docker image reference must spell the path in lowercase** (`ghcr.io/nnyjk/simple-post`): GHCR stores the image under the lowercased path, and the docker CLI refuses a reference whose path contains an uppercase letter (`invalid reference format: repository name must be lowercase`). `github.repository` keeps the owner's original case (`Nnyjk/simple-post`), so pasting it into a docker command produces a command that does not run. The release notes and the release checklist therefore spell the path out in lowercase, and `src/__tests__/release-image-ref.test.ts` pins that spelling. `publish-image.yml` still hands `${{ github.repository }}` to `docker/metadata-action`, which lowercases the path before pushing — the release notes cannot do the same, because they are plain text the user copies.

The smoke test asserts the **response body**, not the status line: an unrouted path falls through to the ServeDir SPA fallback and returns `200 text/html`, so a status-only assertion cannot fail. See the `is_public_path` entry under Code Conventions.

**`update_check` / `update_deployment` / `update_apply` 是 dual-transport 唯一的例外，而且这个不对称是刻意的。** `update_check` 两处都有：`src-tauri/src/commands/update.rs` 的命令与 `GET /api/update/check` 都调 `update_api::check`，因此两条传输拿到的是同一份线上 release 正文（同一个进程内缓存，TTL 6 小时，`force` 绕过 TTL 但同一进程 60 秒内最多强制一次；失败的响应不进缓存）。拿到结论时 `update_api::check` 把那一刻写进 `preferences` 的 `update.last_checked_at`，`update_deployment` 再把它作为 `lastCheckedAt` 回来——浏览器刷新会丢掉渲染层那份 `updateInfo`，设置页的「上次检查」因此以它为回退。`update_deployment` 与 `update_apply` **只在 `serve-web`**：它们回答「这台机器怎么更新」，桌面上这件事由 updater 插件负责，故 `src-tauri/src/lib.rs` 刻意不注册这两条，`src/stores/update-slice.ts` 的桌面分支一次也不调它们（调了只会拿到「command not found」）。谁要加桌面侧实现，先回答「这台机器怎么更新」是谁的问题。

**桌面端看到的「这一版改了什么」不来自 `latest.json`。** `release.yml` 的 `releaseBody` 是构建期模板，写的是安装说明，tauri-action 把它抄进 `latest.json` 的 `notes`；正文里的「这一版的改动」由 `npm run release` 生成并写回 release，`latest.json` 的 `notes` 仍然只有发布模板里的安装说明。故 `update-slice.ts` 在插件报出新版之后另调一次 `update_check` 取线上正文，`latest.json` 那份 `notes` 只在线上正文取不到时显示。

**`update_apply` 有两道门，必须同时成立：部署声明了 `SIMPLE_POST_UPDATE_COMMAND`（非空白），且服务端跑在口令模式。** 理由是威胁模型而不是便利：能触发 `apply` 的人就是拿到 bearer 口令的人，而没设口令的部署对任何能访问 `/api/*` 的调用方开放，让它执行一条命令等于交出那台机器。命令只从环境变量读，**不接受请求体**——接受请求体等于把「执行任意命令」交给调用方，而这道闸的语义是「按运维声明的那一种方式更新本机」。stdout / stderr 各截到 8 KiB，命令 120 秒后被杀。

**版本比较会切掉 `-` 后缀（`version.rs::parse`），故 `0.1.34-rc1` 与 `0.1.34` 视为同版。** 取舍是「-rc1 算不算新版」没有可靠答案，而逐段数字比已经挡掉了字典序；代价是 `0.2.0-rc1` 不会判成比 `0.1.99` 新，这一条由发布流程负责：`check.rs` 把 `draft` / `prerelease` 的 release 判成 `no_release`，预发布也不挂在 `releases/latest` 上。

**更新包的签名私钥不进仓库，只进两个 GitHub Secrets。** `TAURI_SIGNING_PRIVATE_KEY` 与 `TAURI_SIGNING_PRIVATE_KEY_PASSWORD`（后者是空串）只在 `release.yml` 里读；缺前者时该工作流把 `bundle.createUpdaterArtifacts` 改成 `false`、删掉 `plugins.updater`、打一条 warning，本次只产出安装包，应用内自动更新保持不可用。这是刻意的降级——`tauri build` 在 `createUpdaterArtifacts: true` 且没有密钥时会在打包末尾签名失败，让整次发布变红。不要把它「修」成构建失败。

**latest.json 的 `platforms.*.url` 必须是 release 的下载地址，不能是 `api.github.com` 的资产端点。** `releaseDraft: true` 时 tauri-action 把资产表里的 API 端点写进 `latest.json`（`https://api.github.com/repos/<owner>/<repo>/releases/assets/<id>`），而那个端点是 API 端点，不是下载端点：它要求请求带 `User-Agent`，不带时返回 `403 Forbidden`（`Request forbidden by administrative rules`），而 tauri-plugin-updater 用的 reqwest 默认不发 `User-Agent`，所以 0.1.35 → 0.1.36 的应用内更新拿到 `403`；即使改成带上 `Accept: application/octet-stream`，那个端点也只是 `302` 去文件，不带就只回资产元数据 JSON。故 `release.yml` 在三个矩阵作业之后还有后置作业 `fix-updater-json`，它跑 `scripts/rewrite-updater-json.mjs`，把每一处 url 换成该资产的公开下载地址（`https://github.com/<owner>/<repo>/releases/download/<tag>/<asset>`）再写回同一个 release。草案资产的 `browser_download_url` 是 `…/releases/download/untagged-<hash>/…`（发布后不再指向本包），故草案按 `tag` 与资产名拼地址。**它按 `repos/<owner>/<repo>/releases?per_page=100` 列表找 release，不走 `releases/tags/<tag>`**：by-tag 端点对草案返回 404（`{"message":"Not Found"}`），而这个作业必然在草案阶段运行（`needs: release` + `releaseDraft: true`），走 by-tag 每次发布都会红。这一步不能删：删了它，每一次发布出去的最新包都装不上，而发布流程本身是绿的。认不出的 url（未知资产 id、既不是 API 端点也不是 github.com 地址）脚本直接抛错，不静默留下一个坏地址。没有 `TAURI_SIGNING_PRIVATE_KEY` 时本次发布不产 `latest.json`，脚本查到资产表里没有这个文件就打印一行说明并以 0 退出，作业保持绿——与上面「缺密钥时发布流程刻意不失败」那条一致。

**安装路径与产物名跟随 `productName`，产品名只出现在文案里。** `src-tauri/tauri.conf.json` 的 `productName` 是 `simple-post`：bundler 用它拼 NSIS 的 `$INSTDIR`（默认 `currentUser` → `%LOCALAPPDATA%\${PRODUCTNAME}`）、卸载项 `DisplayName`、开始菜单与桌面快捷方式，以及安装包文件名（`simple-post_<version>_x64-setup.exe`；deb / AppImage / macOS `.app` 用同一份值）。窗口标题、`shortDescription` / `longDescription`、release 标题写 `Simple Post`——它们不是路径。改这个值等于改安装目录与卸载项，升级不迁移旧目录，所以不要为「好看」把它改回带空格的名字。

**App / window icons have no config knob.** There is no `icon` field on `WindowConfig` and no `defaultWindowIcon` under `app` in Tauri 2 — adding one fails the build with `unknown field` at `tauri-build`. The single lever is `bundle.icon`: `tauri-build` picks the first `.ico` from it and embeds it into the exe as resource `32512`, and tao registers window classes with a null icon, so Windows resolves the taskbar icon from that executable resource. Changing the taskbar icon therefore means **editing `src-tauri/app-icon.svg` and re-running `npm run icons`** — not editing `tauri.conf.json`. Two gotchas in that pipeline: `icon.icns` is not byte-reproducible (`tauri icon` stamps it, so it always diffs), and `tauri icon` parses its SVG with a strict XML parser whose comments may not contain `--`, which makes writing CSS custom-property names like `--primary` in a doc comment fail the whole run.
