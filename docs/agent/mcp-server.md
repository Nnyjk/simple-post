# MCP 守护进程与工具契约

> 从 `AGENTS.md` 拆出的按需文档，原文逐字保留。只有动到本域时才需要读它。

**`api_run_collection` 只在 `full_access` 下可见，逐项目权限门用目标节点的真实归属.** 全局能力门要求 `Capability::Send`（`registry.rs::REQUIRED_CAPABILITY`），故 `read_only` 与 `safe_write` 两档都看不见它；`capability.rs` 的 read_only 分支另有一处显式排除 —— 那个名字既不以破坏性后缀结尾，也不含 `api_call_endpoint` 字样，漏了它就等于把一个会发外网的工具放进只读档。逐项目的权限门用 `db::nodes::root_id_of` 取目标集合 / 模块**真实归属**的项目 id（传字面量 `"global"` 等于没有项目可查，那道门查不到行，权限检查不起作用），并且用 `?` 传播拒绝。

**MCP 的两个发送工具走同一个解析器.** `api_call_endpoint` 按 id 读库再解析；`api_run_request` 把入参拼成一份内存里的 `EndpointDetail`，交给同一个 `variable_fill::resolve_endpoint`。故「调用已存端点」与「发临时请求」不会长出两种请求形状 —— 早先的 `api_run_request` 自带一套拼接规则（先替换后拼接、不认自带 scheme 的 URL），且声明了 `params` / `auth` 却从不读它们，工具描述因此在撒谎。

**MCP 链路**：AI 客户端 → stdio（`stdio_loop.rs`）→ `POST 127.0.0.1:<port>/mcp` → `daemon_http.rs` → `mcp/mod.rs::dispatch` → 能力门（`read_only` / `safe_write` / `full_access`）→ 逐项目权限检查 → 工具处理器 → 共享的 `db` 池 / `http_executor`。那个 `<port>` 是 **MCP 守护进程自己的监听端口**，不是管理平台的端口 —— 主端口只服务 REST API 与 SPA。守护进程端口从数据目录（`SIMPLE_POST_DATA_DIR` 或 `%APPDATA%/simple-post`）里的 `mcp.port` 文件发现；该文件的路径与记录形状住在 `simple_post_core::port_file`，因为写它的（`simple-post-server`）与读它的（`simple-post-mcp`）是两个 crate，这条规则不能写两遍。工具解析出的端点自带变量池（`ResolvedEndpoint.vars`）—— 替换 OAuth2 配置用的就是这个池，故 MCP 从不自己替换 OAuth2 字段。

**端口记录里的配置指纹决定一个还在跑的 daemon 是被收养还是被换掉.** `mcp.port` 文件在 `pid` / `port` / `bind` / `started_at` / `data_dir` / `version` 旁边多了一个顶层键 `config_fingerprint`。指纹是 `http_config::config_fingerprint(&McpHttpConfig)` 算出的规范化 JSON 文本，即那个 daemon 实际在服务的那份监听配置：绑定地址、监听端口、挂载路径、远程开关、允许的 `Host` 名单、允许的 `Origin` 名单。两张名单先排序再拼，故同一组名单换个顺序得到同一个指纹；**监听端口参与计算**——守护进程监听的就是配置里写的那个端口（写 0 时才由 OS 分配），端口变了就是「它现在服务的东西变了」，监管者必须换掉它而不是收养它。端口不进指纹时，监管者会收养那个还在旧端口上服务的 daemon，于是改了端口也不生效。写这个指纹的是监管者，用的正是它 spawn 子进程时传下去的那份配置。监管者启动时的判据是三条同时成立：记录的 PID 活着、`/mcp/healthz` 有响应、记录里的指纹与它要的那份**完全相同**——这时收养那个 daemon，不 kill 不重拉，进行中的 MCP 会话不断。指纹不同，或者记录里读不出指纹（旧版本写的文件），都是「判断不了」，而判断不了的方向是换掉它。`serve-web` 走同一条规则；它从前是无条件把记录里的 daemon 杀掉重拉，那会杀掉桌面应用起的 daemon，挂在它上面的 MCP 客户端随之全部掉线。

**MCP 的端点只有一个：MCP 守护进程自己的监听端口。主端口不再提供 MCP.** `serve-web` 的主 router 不挂 `/mcp`、`/mcp/healthz` 与 `/mcp/tools`；`web_api::build_mcp_only_router` 与 `serve-web` 进程内那个「只服务 MCP」的监听器都已删除。守护进程是子进程，它启动时把持久化的 `mcp.http_config` 那一行读进命令行（`daemon_cli_args`）：绑定地址、监听端口、挂载路径、远程开关与两张白名单。配置里的 `port` 非 0 时守护进程就绑那个端口，写 0 时由 OS 分配。这个形态只有一条机制，故 `host` / `port` / `path` / 白名单在四种部署形态下含义完全一致，没有死字段；改配置只需重启「MCP 进程」卡片里的守护进程，不必重启容器。The listener binds that configured port **inside the container**, so a deployment that publishes it must map a host port onto that same container port — it cannot be mapped back onto 4173. There is deliberately **no `--mcp-port` flag and no `SIMPLE_POST_MCP_PORT`**: the port has to have exactly one home, or the settings and the deployment end up naming two different numbers for the same endpoint. Two traps an agent will hit otherwise: (1) **a container port can carry at most one published port** — two service ports that share a `target` port make the engine drop the second mapping *silently* (the container comes up healthy with one binding, the other host port refuses connections), which is why the MCP endpoint needs a container port of its own instead of reusing 4173; (2) with `PublishMode: host` the published port belongs to the task, so `update_config.order` must be `stop-first` — `start-first` lets the old task hold the host port while the new one starts, and the new container then comes up with a missing port mapping. 配置里的绑定地址只用来区分「只给本机用」与「开放给局域网」：`127.0.0.1` 时那个端口只在本机可达（容器里即外部连不上），`0.0.0.0` 时局域网里的其他机器也能连，那种情况要开 `allowRemote` 并把两张白名单填上——空名单意味着拒绝一切非回环的 `Host`。

**端口只有一个对象管，故「要不要重启」只有一个答案.** MCP 的监听器**就是**守护进程：绑定地址、监听端口、挂载路径、远程开关与两张白名单全都在它启动时读进命令行，改任何一项都要重启它。`McpHttpConfigDto` 因此只带一个布尔 `requires_restart`。设置面板的页脚按这一条说明要重启哪个对象；改端口后不重启守护进程，那个端口上什么也没在监听，而设置面板会说「与已保存的配置一致」。「接入配置」片段在 Web 形态下指向**服务端那台机器上的 MCP 端口**，不是主端口——守护进程跑在服务端进程内部，它的端口要由部署侧发布出来，外部客户端才连得上。

Gate B has two ways to silently become a no-op, and both shipped:

`no_gate_is_passed_the_literal_global` and `no_permission_check_result_is_discarded` in `crates/simple-post-mcp/src/mcp/mod_test.rs` are the regression net. They are source-level rather than behavioural on purpose: a permanently-denied tool still returns a well-formed `PermissionDenied`, so no functional test would notice. The policy itself persists in `preferences` under key `mcp.policy`.

**Addressing a tree by name lives in `core::spec`, and all three hosts share it.** The `*_create` MCP tools accept `if_exists` (`reuse` / `error` / `duplicate`, default `reuse`), and `collection_create` / `endpoint_create` also accept a path (`"订单/明细"`) that builds the collections on the way. The "find it or build it" step itself is `simple_post_core::spec` — `resolve_project` / `resolve_module` / `resolve_collection_path` / `resolve_environment` — so the REST routes, the Tauri commands and the MCP tools cannot drift into three different meanings of the same word. **Two things about it are load-bearing.** First, the permission gate runs **before** the path's collections are created: the anchor node is read to learn the owning project, the gate is checked, and only then are the missing collections written — the other order lets a caller with no rights on a project build nodes inside it. Second, `reuse` returns the existing endpoint **without writing a single field**; `endpoint_update` is the tool that changes an existing endpoint, and it only touches the fields its patch names.

**One interface spec lands in one call, and the orchestration for that lives in `core::spec::upsert`.** `spec_upsert` takes a declarative spec — `project_id`, a module (name or id), a collection path, an optional environment section, and the endpoint itself — and writes the whole thing in **one transaction**: the module is found by name or created, the collections on the path are built level by level, the environment's variables are merged into the environment's existing variables, the base URL goes into the (environment × module) cell, and the endpoint is created. The transaction matters: a spec that fails halfway must not leave a module without an endpoint behind. The orchestration is in core, not in the MCP handler, so the REST route and the MCP tool carry the same semantics: two hosts, two shells, one implementation. **This pair is not the dual-transport invariant described above.** That invariant asks for five coordinated edits including a Tauri command, and the spec has no desktop call site — the paragraph on the two hosts says so. Nobody should add a Tauri command for a spec.

Six rules about that spec are load-bearing, and each of them is a place where the obvious implementation is wrong:

1. **The project must already exist.** The spec names it; the tool never creates a project and never changes a permission tier. Creating a project changes who may write to it, and that is an explicit decision, not something a spec does on the side.
2. **The permission gate runs before anything is written.** Gate B is checked against the project the spec names, so a caller with no rights on that project cannot create modules inside it.
3. **`if_exists` governs the endpoint only** — `reuse` (default) returns the existing endpoint and writes nothing, `error` refuses, `duplicate` builds a second one, `update` overwrites the fields the spec names and leaves the others alone. The environment section is **always** applied: it is assembly, and the endpoint's conflict policy says nothing about it. Note that `reuse` and `update` differ from the `*_create` tools' `if_exists` by having a fourth value, and that the endpoint's identity (same parent + same name + same method + same url) means `update` can never change the name, the verb or the path — those three *are* the identity. Because `duplicate` builds a second endpoint, **"applying the same spec twice changes nothing" is only true for the default `reuse`** — the tool description, the guide and the REST route summary all say it that way.
4. **The spec's variables are merged, not written over.** A spec adds to the environment; it does not rewrite it. The variables the spec does not mention stay as they were. `disabled_variables` is merged into the disabled set the same way, and disabling a variable the environment does not have is an error rather than a silent no-op.
5. **A `collection_id` must sit under the module the spec names.** The address lives in the (environment × module) cell, so a spec that names module A and a collection under module B fills one cell and hangs the endpoint under another — the endpoint then resolves against a cell nobody filled. `db::nodes::module_id_of` decides it, and the spec is refused when the two disagree.
6. **The environment a call names must belong to the project.** `api_call_endpoint` / `api_resolve_endpoint` / `api_validate_endpoint` accept an optional `environment_id`, and it is checked against the endpoint's project before anything is resolved: using another project's environment would put that project's variables into this project's requests. The same rule is enforced on the read side — `mcp::resolve_env` refuses to return an environment whose project is not the one it was asked about, so an id written by another tool still cannot leak. **The endpoint row itself carries no environment**: which environment a request resolves against is decided per call (MCP names one) or by the client's current environment (the app), and nothing about that choice is stored.

The input coercion lives in `core::spec::input` rather than in the MCP crate, because `endpoint_create` and `spec_upsert` must agree on it: `KeyValue`'s `id` is minted when omitted, `enabled` defaults to `true`, a payload that looks like a JSON Schema is rejected, and an auth scheme without its credential is rejected. Two implementations of those rules would drift, and the drift would show up as "the same field behaves differently on the two paths".

**The spec lands through two hosts, and they are one implementation with two shells.** The write is `core::spec::upsert`; `simple_post_mcp::spec::ops::upsert` adds the "what is still missing" half and returns one response shape; `simple_post_server::spec_api::upsert` is the server crate's facade; and the two entry points are the MCP tool `spec_upsert` and the REST route `POST /api/spec/upsert`. The desktop shell exports no command for it — `src-tauri/src/commands/spec.rs` holds only the module comment and the test, because no desktop call site reads a spec; a third shell with no reader is dead code, and adding one back is a new capability rather than a restoration. **Only the MCP tool checks the per-project permission tier** — that table governs what an *AI client* may do inside a project, while the REST route is the user's own session and behaves like `nodes_create` (the whole family of write routes skips that tier). The spec's field names accept **both** spellings (`project_id` and `projectId`): the MCP line uses snake_case, the app's line uses camelCase, and both land on the same type, so one spec travels from an AI client to an HTTP caller untranslated — and **every** multi-word field carries its camelCase alias, because `deny_unknown_fields` turns a missing alias into a rejected spec. The REST route sets an explicit `DefaultBodyLimit` (`spec_api::SPEC_BODY_LIMIT_BYTES`, 8 MB) for the same reason the interchange routes set one: a spec whose `body.schema` is a large JSON Schema must not be rejected by the transport with a bare 413. `src-tauri/src/commands/spec_test.rs` is the regression net for that pair — it reads the two sources and asserts they both call the same implementation, and that both spellings really reach the fields.

**A write tool's response carries three extra fields, and they are additions rather than changes.** `created` says whether this call built the thing or handed back an existing one; `created_collections` says which levels of a path were new; `missing` says what is still missing before the request can go out — a base URL cell with no value, or a `{{variable}}` the environment does not define. `missing` is computed from the same code the send path uses (`variable_fill::resolve_base_url` and `core::dynamic::list_names`), so the hint cannot disagree with what happens on the wire. The endpoint body keeps its old shape, so a client already reading it is unaffected.

**`endpoint_create` rejects a field it does not know instead of dropping it.** The schema used to say `additionalProperties: true` while `EndpointCreateArgs` had no `deny_unknown_fields`, so an agent that sent `pre_request_script` had it silently ignored and received a successful response — the script was simply gone, with nothing saying so. `deny_unknown_fields` turns that into an error that names the field. **The same trap was open for the two scripts themselves:** `endpoint_create` hardcoded `pre_request_script` / `test_script` to `None` while only `endpoint_update`'s patch accepted them, so an endpoint with scripts always took two calls.

**MCP resources carry the cross-tool guide, not the per-tool contract.** `daemon_http.rs` answers `resources/list` and `resources/read`; `simple-post://spec-authoring` returns the one-call `spec_upsert` shape, the manual call order for the cases that need one step at a time, the full `endpoint_create` argument shape, and what the extra response fields mean. It is deliberately a **resource** and not part of the tool descriptions: that content applies across tools, while `tools/list` is paid for on every session. `resources_test.rs` is the regression net — it asserts that every tool the guide names is registered, that every argument it shows exists in that tool's schema, and (recursively, because the spec is nested) that every key of the `spec_upsert` template exists in that tool's schema, so the guide cannot drift into describing a tool or a parameter that does not exist.

**The `tools/list` payload has a byte budget, and the token count must be measured with a real tokenizer.** The budget lives in `crates/simple-post-mcp/src/mcp/mod_test.rs` (`TOOLS_LIST_BUDGET_BYTES`, 49 152 bytes). **Do not estimate tokens as "characters ÷ 3"** — that overstates JSON by about 60 %, because a token covers four-plus characters of JSON. The measured shape is **48 324 bytes across 48 tools** — `tiktoken`'s `cl100k_base` measured **9 413 tokens** on the previous 43 952-byte payload, and the current one has not been re-measured, so re-measure before quoting a token count instead of scaling the old figure. The size is taken over the *compact* serialization — the one that actually goes on the wire; the pretty-printed one is 1.65× the bytes for the same content. The count is **UTF-8 bytes**, not characters: `String::len()` counts bytes and the descriptions contain Chinese text, so the byte count of the same payload is larger than its character count. That leaves **828 bytes of headroom** under the 49 152-byte budget — a new tool or a longer description eats into it. `report_the_tools_list_size` prints the per-tool breakdown and writes **two** files — `target/tools-list.json` (compact, the one a tokenizer must be pointed at) and `target/tools-list.pretty.json` (indented, for reading); it asserts nothing and writes files, so it is `#[ignore]`d — run it on demand with `cargo test -p simple-post-mcp -- --ignored --nocapture report_the_tools_list_size`.

**Re-baselining the budget is a last resort, and it has to be written down.** The budget moves when the contract moves: a tool is added, a schema grows a field, or a description has to spell out a rule the agent would otherwise get wrong. The answer to that is to write the new segments short, not to drop the contract. **When the budget moves, record in the same commit what moved it and what the new measurement is**, or the next agent sees a number with no explanation and assumes the budget is arbitrary. The budget went from 43 400 to 44 050 bytes when `endpoint_history` was added: that one tool's schema and description are 577 bytes, and the measurement was 43 952 bytes / 9 413 tokens. It went from 44 050 to 45 200 bytes when `responses` arrived: `endpoint_create`, `endpoint_update` and `spec_upsert` each grew a `responses` schema (one property table listed three times, ~1 000 bytes) while `body_content`'s prose lost the framing detail `body_mode` already documents, for a net **+1 164 bytes**; the measurement was then 45 116 bytes. Issue #12 added `protocol` / `graphql` to `endpoint_create`, `endpoint_update` and `spec_upsert` (including the three-state patch description), which took the compact payload to **47 658 bytes / 48 tools** and the budget to **48 KiB**. `api_run_request` then gained the `protocol` enum (four values) and the `graphql` object — **+666 bytes** — for **48 324 bytes / 48 tools**, still under 49 152.

Two rules follow from the budget. First, **the tool description says what the parameter is; the guide says the rules and the examples.** A property description that explains *why* belongs in `simple-post://spec-authoring`, not in the schema, because the schema is paid for on every session while the guide is read on demand. Second, **the schema keeps the contract**: property names, types, enums, which fields are required, and the one-line facts that prevent a wrong call (`content` is the payload and `schema` is the definition; a base URL needs a module cell; `if_exists=reuse` writes nothing). The existing `schema_test.rs` enforces the part that is easy to lose: every `body_mode` value the enum advertises has to be named in the prose of `body_mode` or `body_content`, because a mode the prose never describes is one the agent fills with the wrong shape.

**An MCP client must not hardcode an OS-assigned daemon port.** `mcp.http_config` 的 `port` 写 0 时端口由操作系统分配，每次重启都会变，写死的 `http://127.0.0.1:<port>/mcp` 端点会跟着下一次重启悄悄失效——改 `mcp.policy` 也要重启守护进程，于是改一次策略就断一次连接。**要让地址固定下来，就在「连接 → HTTP 服务配置」里把「端口」填成一个具体数字并重启守护进程**：守护进程就监听那个端口，此后客户端配置里的地址不随重启变化。`simple-post-mcp.exe` 这边：`--url` 省略时它从 `mcp.port` 文件里发现运行中的守护进程端口（`simple_post_core::port_file::read_port`），给定时它把 `--url` 当作 base 并在后面接 `/mcp`（传 `…/mcp` 会得到 `/mcp/mcp` → 404）。它**不再**默认指向主端口 4173——主端口不提供 MCP，连过去只会拿到 SPA 壳。
