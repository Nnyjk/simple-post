# Repository Guidelines

## Project Overview

`simple-post` is a desktop API client/debugger (Postman-like, Windows-first) whose core differentiator is a **built-in MCP server**: external AI clients (Claude Desktop, Cursor, Cline) can list/search/run/mutate endpoints through 52 MCP tools. Stack: **Tauri 2 + React 18 + TypeScript** frontend over a **Cargo workspace** (SQLite via `rusqlite`, `reqwest`, `axum`), shipping three shapes off one Rust core — the Tauri desktop app, the headless `serve-web` REST+SPA host, and the `simple-post-mcp` bridge. The bridge ships as a **compiled binary only** (release artefact / `cargo install`); there is no npm package for it — see Runtime/Tooling Preferences.

Docs are partly Chinese (`README.md`, the two crate READMEs); code/identifiers are English. Division of labour: `README.md` is the human-facing product doc (positioning, distribution shapes, deployment constraints, roadmap); this file is the **agent runtime contract** (invariants, traps, file map). When the two would repeat each other, a fact belongs here only if an agent would break it by not knowing it.

## Architecture & Data Flow

Six runtime pieces:

| Piece | Path | Role |
|---|---|---|
| Tauri shell + CLI | `src-tauri/` | Desktop GUI and the `#[tauri::command]` surface (`commands/`). Everything else is re-exported from the server crate below, so `crate::daemon_supervisor` / `crate::web_api` still resolve here |
| Server host | `crates/simple-post-server/` | `serve-web` REST/SPA server, daemon supervisor, port registry, bearer auth, wire DTOs. **No Tauri by default** — this is what the Docker image builds |
| Core library | `crates/simple-post-core/` | Domain models, SQLite (`db/`), `http_executor`, `permissions`, `mcp_metrics`, `error` — headless, no Tauri/axum dep |
| Interchange | `crates/simple-post-interchange/` | 导入导出转换层：外来格式 ↔ `domain` 标准格式。**`simple-post-mcp` 刻意不依赖它**（scope 内无 MCP 导入导出工具），故 MCP 二进制不必背上 YAML 解析器与两套外来格式模型。契约与已核实的陷阱见其 `README.md` |
| MCP server | `crates/simple-post-mcp/` | JSON-RPC 2.0 dispatch (52 tools), axum HTTP daemon, stdio bridge |
| Frontend | `src/` | React 19 + Vite 8 + Zustand 5 + Tailwind 4 + CodeMirror 6 |

**Interchange: `ir` 不是 `domain` 的别名。** 三条边性质不同：`format → ir` **有损**（故必须走 `Diagnostic`，不能静默丢）；`ir → domain` 无损全函数（补 id / `root_id` / 时间戳）；`domain → ir` 是投影（host 不在 endpoint 上，导出得自己选环境）。IR 必须自有的三条理由：预览阶段节点**还没有 id**、`domain` 无处安放诊断、导出需跨 `nodes`/`endpoint_details`/`projects`/`environments` 四表。指纹去重算在 IR 上，故两种导入器互相认得。**不要**为它加 `SCHEMA_VERSION`。

**Interchange 的依赖方向是 `server → interchange → core`**，它自己不含 Tauri 也不含 axum。导入 / 导出的**编排**（取内容、折成线形状、落库、产出文档）住在 `crates/simple-post-server/src/interchange_api.rs`，**不是**在 Tauri command 里 —— 这是 dual-transport invariant 的直接后果：那一层若写在某一侧，另一侧会静默少一半。四个薄壳入口两处都有（`src-tauri/src/commands/interchange.rs` 与 `web_api/routes/interchange.rs`），它们都只调 `interchange_api` 的四个函数。`interchange_api::import_commit` 走 `commit_in_tx` 而不是 `commit`：环境必须与树同事务，而 `with_tx` 闭包拿不到第二个连接（`BEGIN IMMEDIATE` 会自死锁）。

**项目、服务与资源树节点的创建编排也住在 server crate.** 建项目、建服务、选默认服务（★）、建节点这四段编排过去各写一遍：Tauri 命令在 `src-tauri/src/commands/{projects,base_url_defs,nodes}.rs`，REST 路由在 `crates/simple-post-server/src/web_api/routes/{projects,base_url_defs,nodes}.rs`。两边各拼一次那一行、各自决定 id 归谁铸、各自推导 `root_id`，于是同一个问题有两个答案，而没有一处会提醒它们分叉了。现在四段编排住在 `crates/simple-post-server/src/project_api.rs` 的四个函数里，两侧薄壳只负责**线格式**：REST 侧解析两种 body 形状（`POST /api/projects` 的 `{name, opts}` 与打平的 `Project` 两种形状都还在用）、`ensure_server_id` 补 id，Tauri 侧把 `kind` 字符串解析成枚举。MCP 侧**不在**这一层：它的 `project_create` 与 `base_url_def_create` 走 `core::spec` 的「按名找或建」（带 `if_exists`），与这里的「照单新建」是两种契约；按项目的权限门只有 `base_url_def_create` 有，`project_create` 刻意不走——项目还不存在，没有归属项目，也就没有可套用的存档权限。回归网分两层：`crates/simple-post-server/src/project_api_test.rs` 是行为用例，`crates/simple-post-server/src/project_api_shells_test.rs` 里的 `both_transports_call_the_shared_layer` 读六个薄壳的源码，要求它们都调 `project_api`、都不再自己拼那一段落库，且 REST 侧那两个收 `Json<Value>` 的薄壳都调 `ensure_server_id(`。

**Interchange 的 `IrNode.key` 是「IR 还没成为节点」的那一半身份**：导入 = 源格式的位置指针（与 `Diagnostic::pointer` 同一套寻址纪律），导出 = `nodes.id`。它是勾选集的成员身份，也是跨两侧引用一个条目的唯一句柄。`#[serde(default)]` 保证没有 `key` 的旧 IR 仍能反序列化。

**The Tauri split, and why it exists.** `src-tauri` links `tauri` unconditionally, so a Linux build of it drags in `libwebkit2gtk` / GTK / X11 — which a container serving `serve-web` needs only to run a GUI it cannot display. The server half therefore lives in `crates/simple-post-server`, and the dependency points one way: `simple-post (Tauri) → simple-post-server → simple-post-core`. Three consequences worth respecting:

1. **The `gui` feature is off by default.** It re-attaches only the three `AppHandle`-taking daemon verbs (`ensure_started` / `start` / `restart`) that emit `daemon://crashed` to the webview. `src-tauri` turns it on; the image build does not. Do **not** move it into `default` to "share more code" — that is the failure the feature exists to avoid.
2. **Wire DTOs are not Tauri-specific.** `McpStatusDto`, `CreateEndpointDetailOpts`, `RestartResult` and friends live in `simple_post_server::dto`, and `http_config.rs` holds the shared read/write helpers. `src-tauri/src/commands/dto.rs` is a `pub use` compatibility surface, not a definition site. A DTO that lands there again re-couples the server to `tauri::State`.
3. **Desktop `simple-post serve-web` still works** and delegates to the same implementation, so `npm run dev:split` and the documented LAN workflow do not regress. There is one implementation, not two.

**Resource tree.** Modules, collections and endpoints all live in **one `nodes` table**, discriminated by `type`. Hierarchy is `parent_id`; the owning project is denormalised onto every row as `root_id` (one indexed read answers "which project", which is both the store's filter and the MCP permission gate's key). Endpoint request configuration — method, url, auth, body, headers, params, tags — is a separate `endpoint_details` row keyed by node id, because those fields are meaningless for a module and the tree never renders them. The logical shape is still Project → Module → **Collection (recursively nestable, unbounded depth)** → Endpoint — with the one relaxation that an endpoint may sit directly under a module, so a single endpoint needs no throwaway collection first — and UI renders it with a recursive component.

The parent/child relationship is an **enforced contract**, not a convention: `ResourceNodeType::may_under` defines that a module may only be top-level, an endpoint may sit under either a collection or a module, and a collection may sit under either a module or another collection. A SQLite trigger and an application-layer check both enforce it. `db::nodes::move_many` refuses any other combination, and the frontend's optimistic `moveNodes` guard mirrors it.

**CLI modes** (`src-tauri/src/main.rs`, clap): default → Tauri GUI; `mcp` → embedded MCP daemon; `mcp-proxy` → stdio bridge; `serve-web` → headless REST + static SPA.

**CRUD flow** — component → Zustand slice (optimistic update) → `invokeCmd()` (`src/lib/tauri-commands.ts`) → Tauri IPC **or** `fetch('<base>/api/…')` → `src-tauri/src/commands/` (desktop) / `crates/simple-post-server/src/web_api/` (browser) → `simple_post_core::db` → `store.db` (WAL).

**HTTP requests** bypass webview CORS: `src/lib/http.ts::sendRequest` → `httpRequest` command → `http_executor.rs` (reqwest).

**Two surfaces, switched on `activeProjectId === ''`** (`src/App.tsx`). `WelcomeScreen` is a full-window page with no top bar, no tree and no tab strip; everything else lives in `WorkspaceShell` (`src/features/workspace/`), which is `lazy()`. The split does three things at once: it keeps the whole workspace — and through it the CodeMirror editors — out of the cold-start chunk; it pairs with the two-layer `bootstrap()` below; and it makes the no-project state genuinely empty instead of a frame full of controls that cannot do anything. `leaveProject()` (the TopBar wordmark) is the way back.

**Settings is a third host, not a third implementation.** The settings singleton is also a *tab*, so it has to be reachable with no project open — otherwise "打开设置" on the welcome screen writes a tab nobody renders and visibly does nothing. `App.tsx` therefore branches on `activeProjectId === '' && activeTabId === SETTINGS_TAB_ID` → `SettingsSurface` (`src/features/settings/SettingsSurface.tsx`), a `lazy()` full-window host that adds only the chrome a standalone surface needs (drag region, 返回, window controls) around **the same** `SettingsPanel` the workspace mounts as a tab. Two hosts, one panel: every section reads from the store rather than props, so the two cannot disagree. `SettingsPanel` gates its env section on `activeProjectId !== ''` — with no project the `新建环境` button would write to `projectId === ''` and fail silently, so it renders a hint instead. Both hosts are `lazy()` and `SettingsPanel` is a shared chunk: do not statically import either from `App.tsx`.

**Two-layer `bootstrap()`** (`src/stores/bootstrap-slice.ts`). Layer 1 is `projects_list` + `request_settings_get`, awaited; it flips `loaded`, which tears down the HTML boot splash. Layer 2 is `nodes_list` + `endpoint_details_list` + `environments_list`, run by `loadWorkspace()` and **not** awaited. Consequences worth respecting: `nodes: []` is ambiguous while `nodesLoaded === false` (render a loading state, never "该项目还没有模块"); layer-2 failures land in `nodesError`, not `bootstrapError`, so a tree failure cannot strand the splash; and `pruneStaleTabs()` no-ops until `nodesLoaded` or it would delete every tab it is supposed to be keeping. The request settings ride along in layer 1 because the settings panel is reachable from the welcome screen — the knobs must be in place before anyone can open it.

**刷新后回到上次停留的项目，而不是回到欢迎页.** 「我在哪个项目里干活」是渲染层的会话事实，故它存在 localStorage 的 `simple-post:prefs` 里（`ui-prefs.ts::readLastProjectId` / `saveLastProjectId`），与主题同一份偏好。**记住它由 store 的订阅负责**（`app-store.ts` 订阅 `activeProjectId` 的变化）—— `activeProjectId` 有三条改法（`openProject` / `setActiveProject`，命令面板跨项目跳接口走的是后者；`deleteProject` 删掉在前面的项目时把用户送到幸存的那个），在各动作里分别写必然漏掉一条，漏掉的后果是记住的项目与实际所在的项目脱节。订阅还顺带把**回滚**算进去：`deleteProject` 失败时 `set(snapshot)` 把 `activeProjectId` 改回去，记住的值跟着回滚；写在乐观 `set()` 里则做不到。`bootstrap()` 在第一层落地后据此进入那个项目 —— 项目已不存在时清掉那条记录并留在欢迎页（这一处要自己写：`activeProjectId` 没变，订阅不会替我们做）。**恢复发生在 `loaded` 翻真之前**：`App.tsx` 按 `activeProjectId` 选界面，晚一步就会先画一帧欢迎页再被换成工作区。两处陷阱：`setTheme` 必须**合并**进那份偏好（整份替换会把记住的项目抹掉，于是换一次主题就把刷新后的落点退回欢迎页）；设置标签不参与恢复——项目里打开设置后刷新回到**项目**，欢迎页里打开设置后刷新回到**欢迎页**。

**偏好键与主题解析只有一处定义。** `simple-post:prefs` 这个键与「什么算合法主题」的判断写在 `src/lib/theme-boot/index.ts`。三处从它派生：`index.html` 的 `<head>` 里那段同步脚本由 `vite.config.ts` 的 `themeBootPlugin` 在**构建期**从这份源码生成（内联脚本是 classic script，浏览器不允许它 import 模块，故插件把唯一的默认导出改写成全局赋值，共享模块因此必须运行时零依赖）；store 的初值与「记住上次停留的项目」也从它读。**校验不能省**：存下来的主题必须过 `resolveTheme`，非法值回落到 `dark` —— 少了这一步，store 会把非法值当主题存下，而 `useIsDark` 只认 `dark` 与 `light`、其余按「跟系统」处理，于是首帧画深色、随后 React 画系统色。

**请求体的两份内容：`content` 是载荷，`schema` 是定义.** `RequestBody` 有两个字段回答不同的问题：`content` 是这一次发出的载荷，`schema` 是文档里那份参数定义（JSON Schema，只用于文档与 OpenAPI 导出，**从不上线**）。两者都是 JSON 对象、形状接近，合成一个输入框时 AI 写接口定义就会把 Schema 当载荷发出去。故界面给它们两个编辑器（`BodyEditor.tsx` 的载荷区与折叠的 Schema 区），MCP 侧的工具描述逐字写明哪个字段放什么，并在 `endpoint_create` / `endpoint_update` 上设一道门：`RequestBody::payload_may_be_a_schema` 判定载荷「看起来是一份 Schema 且 `schema` 还空着」时拒收（`api_validate_endpoint` 报同一条 issue）。真要把一份 Schema 当载荷发时，把同样的内容也写进 `schema` 即可 —— 那是声明意图，不是写反。**残留的 schema 两边都要看得见**：模式切成 `none` 之后 body 里的 schema 仍在（模式切换保留整个 body），界面因此要在 `none` 下仍给出那块 Schema 区（否则用户删不掉它），导出侧则只在真的要写 `requestBody` 时才收集 schema（`mode = none` 的端点没有 requestBody 可引用，收集了就是 `components.schemas` 里没人引用的孤儿定义）。

**请求的装配有两条路径，各自有明确的边界.** 渲染进程组装「这一次发什么」（草稿的未保存编辑只有它知道），后端组装「这个端点是什么」（落库的行）。两条路径的**规则**必须逐条相同，而规则写在两处（TS 的 `prepareRequest` 与 Rust 的 `resolve_endpoint`）—— 故它们由共享样本钉住：`fixtures/resolve-parity.json` 与 `fixtures/multipart-parity.json`，两侧各有一个读取器（`src/lib/__tests__/http-build-parity.test.ts` / `crates/simple-post-mcp/src/variable_fill/resolve_parity_test.rs`，multipart 那对在 `http-build-multipart-parity.test.ts` / `mcp/http_ops/multipart_parity_test.rs`）。**改动任何一条规则就改两处**，否则样本会红。三条易忘的细节：query 里的空格编码成 `%20`（Rust 的 `core::url::percent_encode`，与 JS 的 `encodeURIComponent` 同字符集，**不是** form 编码的 `+`）；multipart 的 `Content-Type` 追加在 header 列表**末尾**（用户自己写过的那条则就地替换它的值）；空 key 的参数不参与查询串，其中的变量也**不**报缺失。

**base URL 的服务链与 OAuth2 的 token 注入同样各写两遍，故也由共享样本钉住.** base URL 的解析规则写在渲染进程侧的 `src/lib/url.ts::resolveEndpointBaseUrl` 与 MCP 侧的 `crates/simple-post-mcp/src/variable_fill/base_url.rs::resolve_base_url_with`；OAuth2 的 token 注入规则写在渲染进程侧的 `src/lib/oauth2.ts::applyOAuth2Token` 与 core 侧的 `crates/simple-post-core/src/oauth2/inject.rs::inject`。两边的**结果**必须一致，否则界面预览的请求与真正发出去的请求不是同一个。样本是 `fixtures/base-url-parity.json`（15 条）与 `fixtures/oauth2-parity.json`（13 条），两侧各有一个读取器（`src/lib/__tests__/base-url-parity.test.ts` / `crates/simple-post-mcp/src/variable_fill/base_url_parity_test.rs`，OAuth2 那对在 `src/lib/__tests__/oauth2-parity.test.ts` / `crates/simple-post-core/src/oauth2/inject_parity_test.rs`）。**改动任何一条规则就改两处**，否则样本会红。样本只覆盖两侧**共有**的那部分规则：Rust 侧多一个 `forced_def_id`（调用方点名服务，MCP 侧用得上），渲染进程侧没有这个概念，故它留在 crate 自己的测试里，不进样本；反过来渲染进程侧多返回的 `definitionName`（界面要显示的服务名）也不比。六条易忘的细节：base URL 的**服务链没有回退层** —— 端点点名的服务项目里没有时解析不出东西，**哪怕环境里那一格有值也不解析**（服务是项目级的，地址不是）；空格子给出空串而不是借用别的模块的格子；`source` 报的是**哪一行选中了服务**（`definition` 是端点自己点名，`default` 是靠项目 ★ 命中），不是哪个格子提供了 URL；OAuth2 的 `token_type` **去掉首尾空白后透传**（`MAC` 不改成 `Bearer`），去空白后是空串时只放裸 token，而 query 档按 RFC 6749 §8.3 只带裸 `access_token`（不带 token 类型）；query 档的**参数名**：判定「是不是空白」用去空白后的值，取值用**未去空白的原值**，故 `" id_token "` 这样的参数名会带着空白进查询串（被编码成 `%20id_token%20`）；header 档**不覆盖**用户自己写的 `Authorization`（大小写不敏感），query 档的参数名与 token 值都过 `encodeURIComponent` 那一套字符集。

**两处「当前值」必须落库，否则两端会各说各话.** 一是**活动环境**：顶栏 ENV 药丸写 `environments.is_active`（`crud-environment.ts::setEnvironmentActive`），MCP 侧发端点时按「端点自绑的环境 → 项目激活的环境」回落（`mcp::resolve_env`）—— 界面自己建的端点从不绑环境，故没有回落就没有 base URL、变量也不替换。二是**请求旋钮**（超时 / 跟随重定向 / 响应体积上限）：存在 `preferences` 表的 `request_settings` 行里（`db::preferences::keys::REQUEST_SETTINGS`），界面在设置面板里改它，MCP 侧发请求时读同一行；两侧的缺省值都是 5120 KB。**同名的那张 `request_settings` 表已被清除**：它从建立起就没有任何读者，现役容器只有 `preferences` 表里的这一行。

**HTTPS 出站设置分两层，合成只有一处。** 全局默认住在 `preferences` 表的 `request_settings` 行里（`RequestSettings.tls`），界面在设置面板的「请求行为」小节里改它；端点自带的住在 `endpoint_details.tls_json` 列里（`EndpointDetail.tls`），`NULL` = 继承全局默认。**端点给了设置就整体取代全局那份**，不是逐字段合并 —— 逐字段合并要求每个字段带「继承 / 自定义 / 清空」三态，界面上多出三倍的开关，且「端点清掉全局的 CA 路径」与「端点没配 CA 路径」在存储上无法区分。合成只有一处：`core::tls::resolve(global, endpoint)`，由 `script::send_with_scripts` 调；桌面端与 REST 端交出「端点自带的」，MCP 端交出「端点自带的或本次调用的覆盖」。**证书只存路径，不存内容**：私钥一旦进库，`GET /api/preferences` 会把整行原样返回（Web 形态下那是给任何持有 bearer 口令的客户端看的），SQLite 文件本身也是一份用户没预期的备份。路径由**运行请求的那台机器**解析：桌面端是本机路径，`serve-web` / Docker 端是服务端容器里的路径。

**PEM 的区块边界必须补齐，否则 `reqwest` 会整段跳过后面的区块。** `reqwest` 的 PEM 解析器按行读区块：某个区块的 `-----END …-----` 后面若没有换行，下一个区块的 `-----BEGIN …-----` 就与它粘在同一行里，解析器把整行当成前一个区块的结尾，于是**后面那个区块被整段跳过**。实测：把「证书.pem」与「私钥.pem」直接首尾相接时，私钥那份读不到，报错是「private key or certificate not found」——而 PEM 本身完全合法。「证书与私钥分两个文件」正是最常见的 mTLS 材料形态，且用户给的文件末尾常常没有换行，故 `core::tls::normalise_pem_boundaries` 在读进来之后先把每个 END 标记后面的换行补上。改这块时不要绕过它。

**`reqwest` 的 TLS 后端是 `rustls-tls`，不是 native-tls。** 两个后果：`danger_accept_invalid_certs` 与 `danger_accept_invalid_hostnames` 要**一起**开（只开主机名那一个会落到另一个分支：证书链照查、主机名不查，与「跳过校验」不是一回事）；而 `danger_accept_invalid_certs` 打开时 rustls 后端会整体换掉证书校验器，信任链（含加进去的自定义 CA）根本不参与，故「跳过校验」与「挂 CA」不必同时开。

**自定义 CA 是**追加**到内置根证书集，不是替换它。** `add_root_certificate` 只是把证书推进 `config.root_certs`，而 reqwest 在 `build()` 时把 `webpki_roots::TLS_SERVER_ROOTS` 一起 extend 进同一个 root store —— 本仓库从未调 `tls_built_in_root_certs(false)`。故「只信任这张 CA」是**错的说法**：内置的公共根证书集照样有效，界面与文档都要写「额外信任」。另一层：这套客户端用的是 reqwest **内置的 Mozilla 根证书列表**（工作区 `Cargo.toml` 里 `reqwest` 开着 `rustls-tls`），**本机证书库不参与** —— 把公司根证书装进 Windows 证书库不会让它被信任。

**证书路径字段要在写入口校验，否则「只存路径」会被用户手滑破掉。** 类型层面挡住了应用自己写证书内容（那几个字段只有路径），但挡不住用户把私钥正文**粘进**路径输入框 —— 那段文本会原样落进 `preferences` 的 `request_settings` 行或 `endpoint_details.tls_json`，而 `GET /api/preferences` 把整行原样返回。故 `TlsSettings::validate()` 拒绝含 `-----BEGIN` / `-----END` 或换行的值，`db::preferences::set_request_settings` 与 `db::endpoint_details::{create,update}` 都在写之前调它。

**MCP 的两个发送工具走同一个解析器.** `api_call_endpoint` 按 id 读库再解析；`api_run_request` 把入参拼成一份内存里的 `EndpointDetail`，交给同一个 `variable_fill::resolve_endpoint`。故「调用已存端点」与「发临时请求」不会长出两种请求形状 —— 早先的 `api_run_request` 自带一套拼接规则（先替换后拼接、不认自带 scheme 的 URL），且声明了 `params` / `auth` 却从不读它们，工具描述因此在撒谎。

**There is no dev-server startup tuning, on purpose.** An earlier `optimizeDeps.noDiscovery` + short `include` block used to guard a measured **11.3 s → 139 ms** cold first request, and it read like a landmine. Under Vite 8 it is inert: with the block the welcome-screen module graph is **9,622 KB / 43 modules**, without it **9,570 KB / 43 modules** — the config still shrinks what the dep *optimizer* does (10 pre-bundled deps instead of 27) but that work is not on the first-paint path, so the bytes the browser actually pulls are unchanged. It was removed rather than carried forward as a false constraint. Do not reintroduce it, and do not treat "optimise startup" as an open item here.

**Served bytes are not perceived dev speed.** Under Vite 8 the same welcome-screen module graph went from 3.2 MB to 9.6 MB (43 modules either way), and the `optimizeDeps` block neither caused nor cured it — yet `npm run dev` is measurably faster on both compile and load. Bytes are a bandwidth fact here, not a latency proxy, so do not go looking for a config to shrink them back. If you do need to measure a bundler change, note that `GET /` measures nothing: it returns `index.html` without ever touching the dep optimizer, and following `import()` measures "load everything" rather than time-to-first-paint. A valid probe has to crawl the *static* import graph from the entry and compare module count plus bytes across the change.

**Vite `manualChunks` must stay a function.** Vite 8 runs on Rolldown, and its compat layer auto-converts most `rollupOptions` — but **not** `manualChunks` in the object form. `manualChunks: { react: [...] }` fails the build outright with `Expected Function but received Object` / `manualChunks is not a function`; only `manualChunks(id) { ... }` works. The object→function conversion is mechanical, but the *intent* behind it is not: CodeMirror and `marked` must stay out of every statically-imported entry, because `manualChunks` hoists the listed modules and their dependency closure into one chunk and Rollup/Rolldown then emit a **static** import for it — which is exactly what put 425 kB of editor on the critical path before the editors became `lazy()`. Verify by reading the emitted chunk graph in `dist/assets` and grepping the entry's static imports: a chunk *listing* alone will not show a static import edge. Under Vite 8 that graph is clean — the first-paint static graph is **5 chunks / ~313 kB raw**, and no CodeMirror or `marked` reachable from any of them. **The entry chunk's own size is not a stable number**: adding a module can make Rolldown inline a shared chunk into it (a 23 kB `utils` chunk became part of the entry when the script editor landed, and the entry grew from 59 kB to 80 kB while the whole graph stayed at 298 kB). That moves bytes between files without moving them off the critical path, so measure the whole static graph, not the entry file — and do not "fix" it by pinning chunks.

**GSAP is not on the critical path.** `src/lib/gsap.ts` pulls core + CSSPlugin (~60 kB raw), so anything it reaches from the entry chunk pays for it on every cold start. That is why `WelcomeScreen`'s entrance is CSS (`.welcome-enter` in `globals.css`) rather than `gsap.from()`, and why `NewItemModal` / `BootstrapErrorBanner` are mounted on `newItem.open` / `bootstrapError` rather than unconditionally — a `lazy()` component fires its import as soon as it is *rendered*, so wrapping them in `<Suspense>` alone still downloads them during first paint. Verify with the dependency-edge probe described under **Vite `manualChunks`**; a chunk listing alone will not show you a static import edge.

**Services (baseUrl) are project-owned; their URLs are per (环境 × 模块 × 服务).** The service *list* is a project-level fact — `base_url_definitions.project_id` only — so two modules can never hold services that share a `name`, and every module sees every service. The *value* is the per-cell question: `environments.module_base_urls_json` is `service_id → module_id → url`, and each cell is independent. A module with no entry for a service has no URL for it and inherits **nothing** — not the project's ★, not another module's. There is deliberately no fallback layer above it; the v1 code reached for `env.base_urls` and then "whatever key happens to exist", which is exactly the silent cross-module bleed this replaced. `resolve_base_url_with` (`crates/simple-post-mcp/src/variable_fill.rs`) is the resolver; the module-less `resolve_base_url` wrapper exists for callers that have no module and now serves tests only.

**Three columns are dead on purpose — do not "clean them up".** `environments.base_urls_json`, `base_url_definitions.module_id` and `base_url_definitions.is_default` are superseded and never read or written by application code. They stay because a `DROP` means rebuilding the table, which means bumping `SCHEMA_VERSION`, and `ensure_current_schema` **deletes every user's store** on a bump. That is why `PRAGMA user_version` is still `3` despite the shape having changed: `module_base_urls_json` arrives additively through `db::ADDED_COLUMNS`, and `db::migrate` repairs rows written by either predecessor layout. An agent tidying "unused columns" here destroys user data. A dead *table* is a different case: the `request_settings` table had no reader at all and was dropped on open — see **A dead table is dropped on open** below.

**MCP flow**: AI client → stdio (`stdio_loop.rs`) → `POST 127.0.0.1:<port>/mcp` → `daemon_http.rs` → `mcp/mod.rs::dispatch` → capability gate (`read_only`/`safe_write`/`full_access`) → per-project permission check → tool handler → shared `db` pool / `http_executor`. Daemon port discovered via `mcp.port` file in the data dir (`SIMPLE_POST_DATA_DIR` or `%APPDATA%/simple-post`).

**The admin platform and the MCP endpoint can be two ports, and the mechanism is a second listener on a second container port.** The dedicated MCP listener is driven by the persisted `mcp.http_config` row — the same row the settings panel's 「连接 → HTTP 服务配置」 card writes: a non-zero `port` makes `serve-web` open a second listener that serves **only** MCP (the daemon router, so the same `mcp::dispatch`, the same pool, the same mount-path alias, the same Host/Origin allowlist, plus the main port's bearer middleware); `port = 0` means no second listener and `/mcp` lives on the main port only. The listener binds that configured port **inside the container**, so a deployment that publishes it must map a host port onto that same container port — it cannot be mapped back onto 4173. There is deliberately **no `--mcp-port` flag and no `SIMPLE_POST_MCP_PORT`**: the port has to have exactly one home, or the settings and the deployment end up naming two different numbers for the same endpoint. Two traps an agent will hit otherwise: (1) **a container port can carry at most one published port** — two service ports that share a `target` port make the engine drop the second mapping *silently* (the container comes up healthy with one binding, the other host port refuses connections), which is why the MCP listener needs a container port of its own instead of reusing 4173; (2) with `PublishMode: host` the published port belongs to the task, so `update_config.order` must be `stop-first` — `start-first` lets the old task hold the host port while the new one starts, and the new container then comes up with a missing port mapping.

Dev split: Vite `5173` proxies `/api` + `/mcp` to axum `4173`.

**Request scripts live in `simple-post-core::script`, and the whole sequence is written once.** A user's JavaScript runs in an embedded QuickJS sandbox (`crates/simple-post-core/src/script/`): the only host capabilities are what one fixed JS prelude hands over (`pm.request` / `pm.environment` / `pm.response` / `pm.test` / `pm.expect` / `console.log`), so "the script cannot reach the filesystem, the network or a process" holds because that path does not exist rather than because each one was disabled. The sequence — assemble the chain → pre-request script → send → test script → write environment variables back — is implemented **once**, in `script::send_with_scripts`; the desktop path (`http_request` / `POST /api/http/send`) and MCP (`api_call_endpoint`) both call it. If you move a step, change it there: a second ordering, written in the frontend or in the MCP handler, is exactly the drift this design exists to prevent.

The chain order is **collection → nested collection → endpoint**, and the pre-request and test phases use the *same* order (Postman's own documentation says so). Do not reverse the test phase — some third-party write-ups claim it runs endpoint-first, and they contradict the upstream docs. Each script is atomic: if it throws or is interrupted, its changes to the request **and to the environment / request-scoped variables** are discarded while its logs and assertions are kept — the chain shares one sandbox, so a leaked value would otherwise be readable by the next script and persisted by it.

**The send carries the scripts that are effective *right now*, not the stored ones.** The renderer sends the endpoint's own `preRequestScript` / `testScript` (the draft first, falling back to the stored value) and the backend overrides the stored ones with them, field by field (a field the payload does not mention keeps the stored value). Otherwise a script the user edited but has not saved yet would not run — the preview and the actual request would describe two different things. The endpoint id is still sent, and it is what assembles the *collection* chain; a draft endpoint has no row, hence no collection chain, but its own two scripts still run.

Two more rules the sequence obeys: the **test phase sees the pre-request phase's environment writes** (Postman lets a pre-request script hand a token to the test script), and a **failed environment write-back does not fail the send** — the request has already happened and the script outcomes are in hand, so the failure is recorded as a script error instead of replacing the response.

**Dynamic variables (issue #109) are GLOBAL assets, and they resolve BEFORE substitution, on each side.** A dynamic variable is a declaration (name → data source → extraction rule → cache TTL); a request body that says `{{sns}}` gets the fetched value at send time. The definition does **not** belong to a project: the `dynamic_variables` table has no `project_id` column, the name is unique across the whole workspace, and any project's endpoint may reference the same definition. That is the whole point — a baseline project and its per-customer distribution projects share one data source instead of redeclaring it. The source endpoint still belongs to a project, and that project is what the fetch reads from.

**The fetch context comes from the definition, not from the consumer.** `core::dynamic::source_context` derives it, so the same `{{name}}` resolves to the same value in every project:

- environment: the one the definition names → otherwise the **first available environment** of the source endpoint's project (ordered by name, so the dropdown's first entry is the one that takes effect);
- service: the one the definition names → otherwise the project's ★ (default service). The service the source endpoint itself binds is **not** in this chain — a definition that names no service always fetches through the project's ★;
- module: the module the source endpoint sits in, because the base URL lives in the (environment × service × module) cell.

`detail.base_url_override` still wins over all three. The form stores `null` for "follow the default" rather than freezing today's value, so renaming a project's first environment does not silently repoint every definition that uses it.

**The old project-scoped tables are dropped on open, not migrated.** `db::schema::migrate` looks for a `project_id` column on `dynamic_variables` and, when it finds one, drops `dynamic_variable_cache` and `dynamic_variables` *before* `SCHEMA_SQL` runs — `CREATE TABLE IF NOT EXISTS` is a no-op over the old file, so the old rows would survive in a table of a different shape. `SCHEMA_VERSION` deliberately stays at 3: `ensure_current_schema` **deletes** a store whose version does not match, so bumping it would wipe every user's projects, environments and tree in order to discard two preview tables. Only those two tables are dropped; everything else in the file is untouched.

**A dead *table* is dropped on open; a dead *column* has to stay.** The `request_settings` **table** (a singleton row, `CHECK id=1`, three columns for the outbound-request knobs) was a leftover: the knobs live in the `request_settings` **row** of the `preferences` table (`db::preferences::keys::REQUEST_SETTINGS`), and that table never had a reader — the settings panel and the MCP send path both read the `preferences` row, never the table. It is gone from `schema.sql`, and `db::schema::migrate` drops it from existing files *after* `SCHEMA_SQL` runs. That order means a `CREATE` copied back into `schema.sql` produces a table that is created and dropped in the same pass — the right way to use the order is "do not copy it", not "copying it is safe". `SCHEMA_VERSION` stays at 3 for the same reason as the two tables above: dropping a table nobody reads changes no row's readability, while a bump deletes every user's store. The difference from the three dead **columns** is the point: a column `DROP` means rebuilding the table, and rebuilding the table means a version bump. **Do not read this as licence to drop columns.**

Three more things an agent will break otherwise:

1. **The value enters the variable pool, it does not patch the assembled request.** The merge rule is "a dynamic variable's value beats an environment variable of the same name; a *disabled* environment variable does not affect a dynamic variable". Both sub-rules hold only because the dynamic values are merged **after** the disabled filter. Substitution happens in two places — the renderer's `prepareRequest` (`src/lib/http-build.ts`) and Rust's `resolve_endpoint_with` (`crates/simple-post-mcp/src/variable_fill/resolve.rs`) — so the resolution step sits in the *caller* of each, not in `script::send_with_scripts`: that function only implements step 7 (script chain → send → write-back), and by the time it runs the substitution has already happened. `core::dynamic::merge_pool` and the renderer's `mergePool` (`src/lib/dynamic-vars.ts`) are two implementations of one rule; `fixtures/dynamic-parity.json` is what pins them together (read by `crates/simple-post-core/src/dynamic/resolve_parity_test.rs` and `src/lib/__tests__/dynamic-parity.test.ts`).
2. **The engine is in core, the fetcher is in the mcp crate.** `core::dynamic` owns the merge rule, the value serialization, the cache decision, the error taxonomy and the single-flight registry; it defines a `SourceFetcher` abstraction. The implementation lives in `crates/simple-post-mcp/src/dynamic/source.rs` because the "reference an endpoint" source shape has to assemble the request with `variable_fill::resolve_endpoint`, which lives in the mcp crate and which core may not depend on. The operations all three consumers share (MCP tools, REST routes, Tauri commands) live in `crates/simple-post-mcp/src/dynamic/ops.rs`.
3. **A failed fetch does not fail the send.** The variable is treated as missing (`{{sns}}` stays literal in the body) and an error is recorded, exactly like a failed script write-back. The degradation order is override value → expired cached value (only when `stale_fallback` is on) → missing. The cache is keyed by (definition × environment) — the environment being the definition's own fetch environment, not the consumer's — and lives in SQLite, because the desktop app, `serve-web` and the MCP daemon are three processes with separate memories. `value_mode`'s `text` and `auto` produce **identical** output — `text` is a declaration that the user will place the value in a string position and bear the escaping themselves; `json` is the only mode that quotes scalars.

**The per-project permission gate of the dynamic-variable tools lands on the source endpoint's project.** The fetch really uses that project's base URL and credentials, so that project is the one whose permission decides the operation (`db::dynamic_variables::source_project_id_of` answers which one it is). `dynamic_var_list` has **no** per-project gate — the definitions have no single owning project to check, exactly like `project_list`; the global `CapabilityPolicy` decides that one. A definition with an inline source has no project to fall on either, so only the global capability decides it. The definition's *environment* and *service* must belong to the source endpoint's project: `check_source_bindings` — a module-private check in `db/dynamic_variables/validation.rs`, not a public path — refuses any other project's.

**A dynamic variable must have exactly one data source, and "no source at all" means the source endpoint was deleted.** `db::dynamic_variables::create` refuses a definition with neither an endpoint nor an inline request, and refuses one with both. The second source column (`source_endpoint_id`) is cleared by the foreign key's `ON DELETE SET NULL` when the endpoint is deleted — so a definition whose two source columns are both empty is exactly the "the data source endpoint is gone" case, and that is how the panel says so (`数据源已删除`). An agent that lets a user save a source-less definition destroys that distinction, and the panel then reports a deleted endpoint where the user simply left the form blank.

**The dynamic-variable panel is a global singleton, not a per-project tab.** Its tab id is the fixed `DYNAMIC_TAB_ID` (not a per-project id), `pruneStaleTabs` never retires it, and the top bar's entry is always visible. It has two hosts over one panel: the workspace tab and `DynamicVariablesSurface` (a `lazy()` full-window host for the welcome screen, like `SettingsSurface`) — the settings singleton already needs the same treatment, and a tab nobody renders is a button that visibly does nothing. The source picker is a **lazily loaded** tree across all projects: `GET /api/nodes/children` fetches one level when a branch is opened (the project level uses `projectId`, because a module's `parent_id` is NULL), and `GET /api/nodes/search` backs the filter with a 250 ms debounce and returns the matching endpoints plus their path. The filter searches **endpoints only** (name, description, URL) — a collection's name does not match the endpoints beneath it, which is what the tree browsing is for.

Its `if` is `!cancelled() && outputs.docker != 'false'` — the fail-closed half, so a broken filter runs the gate instead of reporting green. A skipped job is reported successful, which is why a skipped required check is acceptable.

The smoke test asserts the **response body**, not the status line: an unrouted path falls through to the ServeDir SPA fallback and returns `200 text/html`, so a status-only assertion cannot fail. See the `is_public_path` entry under Code Conventions.

Keep `npm run check` green locally before pushing — CI runs the same checks.

## Code Conventions & Common Patterns

**Error handling.** Rust returns `Result<T, AppError>` (`crates/simple-post-core/src/error.rs`); `AppError` serializes to a stable `{ code: <snake_case>, message }` wire shape — `code` is the contract, `message` is human-facing. MCP tool failures are returned *inside* `CallToolResult` with `is_error: true` (not a JSON-RPC envelope error) so LLM clients can observe them. Frontend never throws for network failure — `ApiResponse.status === 0` signals transport error.

**DB access.** Reads → `db::with_conn`; writes → `db::with_tx` (`BEGIN IMMEDIATE`, 3 retries / 50 ms backoff on `SQLITE_BUSY`). WAL + `foreign_keys=ON` + `busy_timeout=3000`. Complex fields (`KeyValue[]`, `RequestBody`, `AuthConfig`, `tags`) live in `*_json` text columns. New entity SQL goes in `crates/simple-post-core/src/db/<entity>.rs`.

**Partial updates.** Patch types (`ResourceNodePatch`, `EndpointDetailPatch`, `ProjectPatch`, `EnvironmentPatch`, …) use `#[serde(default, deserialize_with = "double_option")] Option<Option<T>>`: missing key = leave unchanged, JSON `null` = clear, value = set (`crates/simple-post-core/src/domain.rs`). Follow this pattern for any new updatable field. Note `ResourceNodePatch::parent_id` is the one place the pattern earns its keep: `Some(None)` promotes a node to the top of its project, which is a real write target rather than "leave alone".

**Serialization.** All domain types: `#[serde(rename_all = "camelCase")]`; TS counterparts in `src/types/domain.ts`. Keep both in sync when adding fields.

**Zustand selectors (infinite-loop hazard).** Equality is `Object.is`; a selector returning a fresh array/object (`.map`, `.filter`, spread) causes infinite re-render. Selectors must return stable references or `.find(...)`; derive filtered lists with `useMemo` in the component. Slices never import each other — they share state via the `AppState` interface and `get()`/`set()`. Verify with `npx tsx scripts/_verify_store.mjs`.

**Zustand 的服务端快照是**初始状态**，故 `renderToStaticMarkup` 渲染不出改过的 store.** `useStore` 把 `api.getInitialState()` 当作 React 的 `getServerSnapshot` 交给 `useSyncExternalStore`，于是服务端渲染读到的永远是 store **创建时**那份状态，测试里那句 `useAppStore.setState(...)` 改不动它 —— 用例却会「看起来跑了」。要在服务端渲染里覆盖某个状态，有两条路：把那段渲染提成**收 props 的组件**（如 `TlsPanel` 那样），或者把判断提成**纯函数**（如 `isRequestSettingsDirty` 那样）。**别把 `setState` 之后的结果当成已渲染的内容去断言。**

**Dual-transport invariant.** Any new backend command needs **five** coordinated edits: handler in `src-tauri/src/commands/<resource>.rs` (re-exported by `commands/mod.rs`, which must use **glob** `pub use` — an item list drops the `#[macro_export]`ed `__cmd__<name>` macro and `generate_handler!` fails with E0433), registration in `src-tauri/src/lib.rs`, a `COMMANDS` constant in `src/lib/tauri-commands.ts`, a route in `crates/simple-post-server/src/web_api/` (the `.route()` registrations live in `web_api/router.rs::build_router`, the handler in the matching `web_api/routes/<resource>.rs`), and a `WEB_ROUTES` entry (if browser-callable). Missing one side breaks either desktop or web mode silently. A DTO both sides need belongs in `crates/simple-post-server/src/dto.rs`, **not** in `commands/` — see the Tauri split above.

**The transfer dialog is one component, not two.** Import and export share `TransferDialog` / `TransferTree` / `TransferNode` / `TransferEndpoint`; the modes differ in the source picker, two export-only settings, and the confirming action. Don't fork the tree or the types per mode — a shared filename is not a shared component. Its state lives in the `useTransfer` hook, **not** a Zustand slice: only `ProjectTree` can open it, so there is no second reader.

**Exported OpenAPI is checked by two outsiders, not by our own parser.** The importer in `simple-post-interchange` is ours too, so it is permanently lenient about its own generator's output — a missing `responses` yields no error, just one silently-absent field in an already-invalid document. So: `openapiv3` (dev-dep) validates against the official model inside `cargo test`, and Redocly (`npm run lint:openapi`, wired into the CI web job) checks rules. **Both read `crates/simple-post-interchange/fixtures/sample-exchange.json`** — the Rust test and `examples/export_sample.rs` start from the same tree, so two hand-written specimens would each cover half of it. `npm run lint:openapi` regenerates the document through the cargo example rather than committing a snapshot, because snapshots go stale. Rule opt-outs live in `redocly.yaml` and each one states why; silencing a rule is not how the next finding gets fixed.

**Export save is native-only, and the split is deliberate.** Tauri goes through `tauri-plugin-dialog` + `tauri-plugin-fs` (dynamically imported — they have no browser implementation, so a static import would make `serve-web` bundle dead Tauri code and throw at runtime); the browser falls back to a Blob + `<a download>`. The `fs` capability is granted **per verb and scoped to `$HOME/**/*`** — `fs:default` would open read and write over the whole user directory for a feature that writes one text file.

**`reloadWorkspace` vs `loadWorkspace`.** The second layer is idempotent (`nodesLoaded` / in-flight guard) so `bootstrap`, `openProject` and the retry button can each call it uncoordinated. An import writes dozens of rows in one transaction and gets back only ids, so refreshing with the idempotent one silently leaves the tree stale. Use `reloadWorkspace` there; do not remove the guard from `loadWorkspace` to "fix" it, or a tree failure strands the boot splash.

**Two things a whole-array replacement must not flatten.** `expanded` lives only in the renderer (the server never stores it), so `reloadWorkspace` has to merge each node's old `expanded` back in **by id** — a plain replacement collapses every branch the user had open (#74). And a service definition lives on the **project row** (`projects[].baseUrlDefinitions`), which is the copy loaded by bootstrap layer 1 and never refreshed afterwards: an import creates the service server-side, so the client must call `refreshProjects` after the commit or the new service is invisible in the 前置 URL table and the endpoint's service picker reads "项目无默认服务" (#84). Manual service CRUD does not need it — `crud-baseurl.ts` keeps `projects` locally in sync.

**Tauri macro gotcha.** `http_request` in `src-tauri/src/lib.rs` must stay **non-`pub`** — marking it `pub` triggers a `__cmd__http_request` identifier collision (E0255) between `#[tauri::command]` and `generate_handler!`.

**App / window icons have no config knob.** There is no `icon` field on `WindowConfig` and no `defaultWindowIcon` under `app` in Tauri 2 — adding one fails the build with `unknown field` at `tauri-build`. The single lever is `bundle.icon`: `tauri-build` picks the first `.ico` from it and embeds it into the exe as resource `32512`, and tao registers window classes with a null icon, so Windows resolves the taskbar icon from that executable resource. Changing the taskbar icon therefore means **editing `src-tauri/app-icon.svg` and re-running `npm run icons`** — not editing `tauri.conf.json`. Two gotchas in that pipeline: `icon.icns` is not byte-reproducible (`tauri icon` stamps it, so it always diffs), and `tauri icon` parses its SVG with a strict XML parser whose comments may not contain `--`, which makes writing CSS custom-property names like `--primary` in a doc comment fail the whole run.

**Routing.** Axum 0.8 path params use `{id}` syntax (`/api/projects/{id}`). The old `:id` form panics at router construction, not at request time, so a missed route takes down every test in the crate at once.

**Naming.** Rust: `snake_case` functions/modules/columns, `PascalCase` types. Tauri commands `snake_case` in Rust, `camelCase` in the frontend `COMMANDS` registry. Test files: `*.test.ts`; Rust tests go in a **sibling** `*_test.rs` file mounted by `#[path]`, not inline (the inline form survives only in a few files under `src-tauri/` — see Testing & QA).

**Source comments — four rules, all binding on Rust and TS sources.** Comments in this repo had drifted into a retrospective style — "This shipped once on x", "both ways to silently become a no-op, and both shipped" — with no rule ever stated, which is how the drift went unnoticed. Four explicit rules now govern every comment. A repaired defect is not a constraint, so narrative about one is dead weight for whoever reads the code next.

1. **Only what holds _now_.** Delete past-tense narrative — `// shipped once on api_call_endpoint`, `// early versions made nginx strip the prefix`, `// used to render a ghost row here`. Keep current invariants — `// may point at a row outside the current list; check membership before use`, `// cannot use sort here: sort is stable and that breaks the server's same-millisecond rowid DESC tiebreak`. The discriminator is not how much a comment says, it is whether the constraint it names still holds. An invariant no reader can reconstruct from the code is worth keeping; a bug that is already fixed is not.
2. **Chinese, terse, one point per comment.** Compress prose to the conclusion plus the reason it matters, and keep only the part of the reason that says what breaks if you write it the obvious way. Do not restate the code — the code is the documentation. One to three lines; use a short list when it genuinely has to expand.
3. **Every clause names its actor.** A comment has to say which code does what, so a reader never has to infer the subject from context they have not read yet. `回退到空串` tells the reader that the resolver returns an empty string; `兜底` tells the reader neither what happens nor which path takes over. Above a declaration the declaration is the actor, so the comment may omit it — but only there. Inside a function body, name the actor.
4. **No borrowed metaphors.** Pick the word that names the mechanism, not the one that paints a picture. 兜底 (fallback), 面板面 (public surface), 心智模型 (mental model), 落地面 (landing spot), 缝 (seam), 锚定 (anchor), 抹平 (flatten) all force the reader to hold an image in their head and decode it. Write 回退, 缺失时用 X, 公开接口, 理解方式, 承载的位置, 两种名字对不上, 保持一致, 统一处理 instead. The test: does the sentence name a concrete code path, value, or rule? A sentence that names only an image gets rewritten.

Identifiers, keywords, API names, column names and wire strings stay as written: they are not translatable prose. A comment that must quote code should quote the smallest fragment that carries the constraint.

Comments are not free. The repo-wide ratio is about 24 comment lines per 100 code lines, and a few files sit above 100%. Before adding a comment, check that it carries a constraint the code cannot show on its own; otherwise it is a third copy of something the reader can already read.

Three hazards specific to this repo. Several regression tests read the source **as text** (`include_str!`), and two of them do *not* skip comment lines — so a prose edit alone can turn them red:

- `mcp/mod_test.rs::no_gate_is_passed_the_literal_global` looks for `check_permission(` and `"global"` in the same `;`-delimited statement. Never write that call shape as a comment example in any **non-test** file under `crates/simple-post-mcp/src/` — `source_files()` skips `*_test.rs` and `mod_test.rs`, so a test file is not scanned, but every other `.rs` file is.
- `mcp/mod_test.rs::no_permission_check_result_is_discarded` flags any file that both calls `check_permission(` and has a line whose first non-blank characters are `.ok();`. In `mcp/permissions.rs` that rules out writing a discarded result on its own line: bind it first (`let found = …; let env = found.ok();`) instead of ending the statement with a bare `.ok();`.
- `daemon_supervisor_test.rs::the_shared_spawn_path_stays_free_of_tauri` does a raw `body.contains(...)` over the whole brace-matched body of `ensure_started_with` for `AppHandle`, `tauri::`, `Emitter` and `EmitterExt`. A comment inside that function naming any of those four makes the test fail. Its own test body is written around exactly this.

Do not loosen any of these tests or delete one to make a comment edit pass. The assertions are worth more than the prose is.

That second test also **pins two functions to one file**, which constrains how `daemon_supervisor.rs` may be split: it brace-matches `ensure_started_with` and `ensure_started` out of `include_str!("daemon_supervisor.rs")`, so both must stay **whole functions in that file**. Moving either one panics the test with "must exist in daemon_supervisor.rs". Extracting `ensure_started_with`'s body into a helper *elsewhere* is worse than failing: the scan would pass vacuously while the real invariant rotted. The invariant is that the shared spawn path never touches a Tauri type — otherwise the `--lib` test binary gains `comctl32!TaskDialogIndirect` and fails to load with `0xc0000139`. Any helper split out of it must be `AppHandle`-free too.

**Oversized files are facades over same-named module directories.** A file that once exceeded ~500 lines now keeps only its module map and `pub use` re-exports; the bodies live in `<name>/<unit>.rs` (Rust 2018 resolves `mod unit;` inside `foo.rs` to `foo/unit.rs`, so the file grows a directory without moving). Import paths are unchanged, which is what lets `simple-post-mcp` / `simple-post-server` / `src-tauri` keep compiling against a refactored `simple-post-core`. **When splitting, a facade must re-export the public surface, not move it** — and a `#[path]` test mount keeps pointing at the file that declares the `mod`, so a split test file needs its own mount rather than being merged into a neighbour.

**TypeScript uses the same shape.** `src/lib/http-build.ts` keeps the public names and re-exports the bodies from `src/lib/http-build/*.ts`; `src/types/domain.ts` re-exports from `src/types/domain/*.ts` with `export *`. The import path (`@/lib/http-build`, `@/types/domain`) and the bundler's resolution both stay put: a file wins over a same-named directory, so `vite build` still resolves the facade — verified by running the build, not just `tsc`.

**Async/concurrency.** tokio multi-thread runtime; metrics via `AtomicU64` with `Ordering::Relaxed`; `port_registry.rs` uses OS atomic file creation (`create_new`) to prevent multi-instance races.

**MCP stdout discipline.** In `simple-post-mcp`, stdout carries *only* JSON-RPC frames; all logging, panics, and `__mcp_metrics__{…}` telemetry go to **stderr**. Non-JSON on stdout crashes AI clients.

**The script sandbox inherits that discipline, and it is enforced by a test.** `simple-post-core::script` is linked into the MCP daemon, so a `println!` in it corrupts an AI client's stream. `console.log` from a user script goes into an in-memory array (`stdout_test.rs` scans the module's sources for `println!` / `print!` / `dbg!` and fails the build). Two more rules for the same module: **no panics** — the release profile is `panic = "abort"`, so a panic in the script path takes the whole process down — and **the engine's memory limit only works with the default allocator**, so the `rust-alloc` / `allocator` features of `rquickjs` must stay off (with a custom allocator `set_memory_limit` is a silent no-op, and the memory ceiling this project promises would be a lie). The interrupt handler is what makes a timeout real: it returns `true` and the engine raises an *uncatchable* exception, so an endless loop is interrupted rather than waited out. The script phase runs inside `spawn_blocking` — the engine is synchronous and CPU-bound, and running it on an async worker stalls the runtime.

**MCP permissions — two gates, both fail-closed.** Default policy is `read_only`; mutating tools (`env_create`, `endpoint_update`, …) return `is_error: true` until the user raises the tier. **Gate A (global):** `mcp::tool_descriptors` filters `tools/list` by `REQUIRED_CAPABILITY` under the policy the user picked in Settings, and `mcp::dispatch` re-checks before the handler — so an AI client cannot bypass it by calling `tools/call` directly, it just gets `AppError::PermissionDenied`. A tool with **no** capability row is treated as unclassified and denied, not allowed. `Capability` is a total order `Read < Create < Update < Delete < Send`; `Send` means outbound HTTP and is `full_access`-only — that is the deliberate "safe write ≠ free outbound" boundary. **Gate B (per-project):** `required_permission()` over the `permissions` table (`Read < ReadCall < Full`, default `ReadCall`); an unknown tool name is treated as `Full`.

Gate B has two ways to silently become a no-op, and both shipped:

1. **Wrong project id.** Handlers must resolve the real owning project and pass it — `db::nodes::root_id_of` for anything that is a `nodes` row, `db::base_url_defs::project_id_of` for a baseUrl definition, `db::environments::lookup_project_id` for an environment. Passing the literal string `"global"` looks harmless and is not: `agent_permissions.project_id` is an FK to `projects(id)` and ids are minted `proj_<millis>`, so the lookup finds no row, falls back to `Permission::default()` = `ReadCall`, and every write tool — which requires `Full` — is denied. **The tool is then permanently dead while still looking correctly registered.** This shipped on five `env_*` tools, then again on `module_update` / `module_delete` / `collection_create` / `base_url_def_update` / `base_url_def_delete`. `project_create` and `project_list` have no owning project by construction and correctly skip Gate B entirely — Gate A governs them.
2. **Discarded result.** `check_permission(..).await.ok()` compiles, passes review by eye, and throws the `PermissionDenied` away, so the gate never blocks. It shipped on `api_call_endpoint` — the one tool that performs an outbound HTTP request. Always propagate with `?`.

`no_gate_is_passed_the_literal_global` and `no_permission_check_result_is_discarded` in `crates/simple-post-mcp/src/mcp/mod_test.rs` are the regression net. They are source-level rather than behavioural on purpose: a permanently-denied tool still returns a well-formed `PermissionDenied`, so no functional test would notice. The policy itself persists in `preferences` under key `mcp.policy`.

**Adding an MCP tool requires TWO registry edits, not one.** A tool added to `tool_table()` without a matching `REQUIRED_CAPABILITY` row **escapes the global capability gate entirely** — both the `tools/list` filter and the `dispatch` pre-flight treat a missing row as unclassified and now fail *closed* (deny), but the tool becomes invisible/unusable rather than policy-compliant. This actually shipped once: `module_move` and `collection_move` were registered without rows and bypassed the user's `read_only` choice. `every_registered_tool_has_a_capability` (and its inverse `every_capability_row_names_a_registered_tool`) in `crates/simple-post-mcp/src/mcp/mod_test.rs` is the regression net — if you add a tool and those tests fail, add the row with the correct `Capability` (`Read < Create < Update < Delete < Send`; `Send` means outbound HTTP and is `full_access`-only).

**Addressing a tree by name lives in `core::spec`, and all three hosts share it.** The `*_create` MCP tools accept `if_exists` (`reuse` / `error` / `duplicate`, default `reuse`), and `collection_create` / `endpoint_create` also accept a path (`"订单/明细"`) that builds the collections on the way. The "find it or build it" step itself is `simple_post_core::spec` — `resolve_project` / `resolve_module` / `resolve_collection_path` / `resolve_environment` — so the REST routes, the Tauri commands and the MCP tools cannot drift into three different meanings of the same word. **Two things about it are load-bearing.** First, the permission gate runs **before** the path's collections are created: the anchor node is read to learn the owning project, the gate is checked, and only then are the missing collections written — the other order lets a caller with no rights on a project build nodes inside it. Second, `reuse` returns the existing endpoint **without writing a single field**; `endpoint_update` is the tool that changes an existing endpoint, and it only touches the fields its patch names.

**One interface spec lands in one call, and the orchestration for that lives in `core::spec::upsert`.** `spec_upsert` takes a declarative spec — `project_id`, a module (name or id), a collection path, an optional environment section, an optional service section, and the endpoint itself — and writes the whole thing in **one transaction**: the module is found by name or created, the collections on the path are built level by level, the environment's variables are merged into the environment's existing variables, the base URL goes into the (environment × service × module) cell, and the endpoint is created. The transaction matters: a spec that fails halfway must not leave a module without an endpoint behind. The orchestration is in core, not in the MCP handler, so the REST route and the Tauri command can carry the same semantics — the dual-transport invariant applies here exactly as it does to the interchange layer.

Six rules about that spec are load-bearing, and each of them is a place where the obvious implementation is wrong:

1. **The project must already exist.** The spec names it; the tool never creates a project and never changes a permission tier. Creating a project changes who may write to it, and that is an explicit decision, not something a spec does on the side.
2. **The permission gate runs before anything is written.** Gate B is checked against the project the spec names, so a caller with no rights on that project cannot create modules inside it.
3. **`if_exists` governs the endpoint only** — `reuse` (default) returns the existing endpoint and writes nothing, `error` refuses, `duplicate` builds a second one, `update` overwrites the fields the spec names and leaves the others alone. The environment and the service sections are **always** applied: they are assembly, and the endpoint's conflict policy says nothing about them. Note that `reuse` and `update` differ from the `*_create` tools' `if_exists` by having a fourth value, and that the endpoint's identity (same parent + same name + same method + same url) means `update` can never change the name, the verb or the path — those three *are* the identity. Because `duplicate` builds a second endpoint, **"applying the same spec twice changes nothing" is only true for the default `reuse`** — the tool description, the guide and the REST route summary all say it that way.
4. **The spec's variables are merged, not written over.** A spec adds to the environment; it does not rewrite it. The variables the spec does not mention stay as they were. `disabled_variables` is merged into the disabled set the same way, and disabling a variable the environment does not have is an error rather than a silent no-op.
5. **A `collection_id` must sit under the module the spec names.** The base URL lives in the (environment × service × module) cell, so a spec that names module A and a collection under module B fills one cell and hangs the endpoint under another — the endpoint then resolves against a cell nobody filled. `db::nodes::module_id_of` decides it, and the spec is refused when the two disagree.
6. **The endpoint's own environment and service must belong to the project.** `endpoint.environment_id` and `endpoint.base_url_definition_id` are checked against `project_id` before anything is written: binding another project's environment would put that project's variables into this project's requests. The same rule is enforced on the read side — `mcp::resolve_env` refuses to return an environment whose project is not the one it was asked about, so a binding written by another tool still cannot leak.

The input coercion lives in `core::spec::input` rather than in the MCP crate, because `endpoint_create` and `spec_upsert` must agree on it: `KeyValue`'s `id` is minted when omitted, `enabled` defaults to `true`, a payload that looks like a JSON Schema is rejected, and an auth scheme without its credential is rejected. Two implementations of those rules would drift, and the drift would show up as "the same field behaves differently on the two paths".

**The spec lands through three hosts, and they are one implementation with three shells.** The write is `core::spec::upsert`; `simple_post_mcp::spec::ops::upsert` adds the "what is still missing" half and returns one response shape; `simple_post_server::spec_api::upsert` is the server crate's facade; and the three entry points are the MCP tool `spec_upsert`, the REST route `POST /api/spec/upsert`, and the Tauri command `spec_upsert`. **Only the MCP tool checks the per-project permission tier** — that table governs what an *AI client* may do inside a project, while the REST route and the Tauri command are the user's own session and behave like `nodes_create` (the whole family of write routes skips that tier). The spec's field names accept **both** spellings (`project_id` and `projectId`): the MCP line uses snake_case, the app's line uses camelCase, and both land on the same type, so one spec travels from an AI client to an HTTP caller untranslated — and **every** multi-word field carries its camelCase alias, because `deny_unknown_fields` turns a missing alias into a rejected spec. The REST route sets an explicit `DefaultBodyLimit` (`spec_api::SPEC_BODY_LIMIT_BYTES`, 8 MB) for the same reason the interchange routes set one: a spec whose `body.schema` is a large JSON Schema must not be rejected by the transport with a bare 413 while the desktop command accepts the same spec. `src-tauri/src/commands/spec_test.rs` is the regression net for that triple — it reads the three sources and asserts they all call the same implementation, that the command binds the spec under the single key `spec` (the Tauri macro binds by parameter name, so a renamed parameter breaks the desktop shape while the browser shape keeps working), and that both spellings really reach the fields.

**A write tool's response carries three extra fields, and they are additions rather than changes.** `created` says whether this call built the thing or handed back an existing one; `created_collections` says which levels of a path were new; `missing` says what is still missing before the request can go out — a base URL cell with no value, or a `{{variable}}` the environment does not define. `missing` is computed from the same code the send path uses (`variable_fill::resolve_base_url_with` and `core::dynamic::list_names`), so the hint cannot disagree with what happens on the wire. The endpoint body keeps its old shape, so a client already reading it is unaffected.

**`endpoint_create` rejects a field it does not know instead of dropping it.** The schema used to say `additionalProperties: true` while `EndpointCreateArgs` had no `deny_unknown_fields`, so an agent that sent `pre_request_script` had it silently ignored and received a successful response — the script was simply gone, with nothing saying so. `deny_unknown_fields` turns that into an error that names the field. **The same trap was open for the two scripts themselves:** `endpoint_create` hardcoded `pre_request_script` / `test_script` to `None` while only `endpoint_update`'s patch accepted them, so an endpoint with scripts always took two calls.

**MCP resources carry the cross-tool guide, not the per-tool contract.** `daemon_http.rs` answers `resources/list` and `resources/read`; `simple-post://spec-authoring` returns the one-call `spec_upsert` shape, the manual call order for the cases that need one step at a time, the full `endpoint_create` argument shape, and what the extra response fields mean. It is deliberately a **resource** and not part of the tool descriptions: that content applies across tools, while `tools/list` is paid for on every session. `resources_test.rs` is the regression net — it asserts that every tool the guide names is registered, that every argument it shows exists in that tool's schema, and (recursively, because the spec is nested) that every key of the `spec_upsert` template exists in that tool's schema, so the guide cannot drift into describing a tool or a parameter that does not exist.

**The `tools/list` payload has a byte budget, and the token count must be measured with a real tokenizer.** The budget lives in `crates/simple-post-mcp/src/mcp/mod_test.rs` (`TOOLS_LIST_BUDGET_BYTES`, 43 400 bytes ≈ 9 200 tokens). **Do not estimate tokens as "characters ÷ 3"** — that overstates JSON by about 60 %, because a token covers four-plus characters of JSON. The measured shape is **42 735 bytes ≈ 9 079 tokens** (`tiktoken`'s `cl100k_base`, over the *compact* serialization — the one that actually goes on the wire; the pretty-printed one is 1.7× the bytes for the same content). The count is **UTF-8 bytes**, not characters: `String::len()` counts bytes and the descriptions contain Chinese text, so the same payload is 42 673 characters but 42 735 bytes. `report_the_tools_list_size` prints the per-tool breakdown and writes **two** files — `target/tools-list.json` (compact, the one a tokenizer must be pointed at) and `target/tools-list.pretty.json` (indented, for reading); it asserts nothing and writes files, so it is `#[ignore]`d — run it on demand with `cargo test -p simple-post-mcp -- --ignored --nocapture report_the_tools_list_size`.

**Re-baselining the budget is a last resort, and it has to be written down.** The budget was raised twice: from 38 800 to 41 400 **characters** (the unit before this change), when path parameters (`path_params`) entered the contract of three tools (`endpoint_create`, `endpoint_update`, `spec_upsert`) and `api_call_endpoint` had to document its `overrides` fields; then from 41 400 to 43 400 **bytes** (the unit now), when HTTPS 出站设置（`tls`）entered the schema of `endpoint_create` / `endpoint_update` and the `settings_override` description of `api_run_request` / `api_call_endpoint`. The contract grew, so the payload grew — the answer to that is to write the new segments short, not to drop the contract. **When the budget moves, record what moved it in the same commit**, or the next agent sees a number with no explanation and assumes the budget is arbitrary.

Two rules follow from the budget. First, **the tool description says what the parameter is; the guide says the rules and the examples.** A property description that explains *why* belongs in `simple-post://spec-authoring`, not in the schema, because the schema is paid for on every session while the guide is read on demand. Second, **the schema keeps the contract**: property names, types, enums, which fields are required, and the one-line facts that prevent a wrong call (`content` is the payload and `schema` is the definition; a base URL needs a service; `if_exists=reuse` writes nothing). The existing `schema_test.rs` enforces the part that is easy to lose: every `body_mode` value the enum advertises has to be named in the prose of `body_mode` or `body_content`, because a mode the prose never describes is one the agent fills with the wrong shape.

**Never mint an id from a millisecond clock.** `format!("mod_{now}")`, `format!("col_{now}")`, `format!("proj_{now}")` and `now_ms().to_string()` (that last one was the environment id) all produced the same primary key for two creations inside one millisecond, so a batch create collided on `nodes.id` / `environments.id` and the second one failed with a constraint error. `domain::uid()` is the only id source in the repo; `core::spec` uses it for everything it creates, and the `ep_` / `mod_` / `col_` / `proj_` / `env_` prefixes are kept on top of it.

**MCP wire-format field names are camelCase, and the hand-written JSON is a third site.** `ToolDescriptor.input_schema` and `CallToolResult.is_error` shipped as snake_case while the spec spells them `inputSchema` and `isError`, so all 52 tools reached a compliant client as argument-less and every failed call read as a success — with every unit test green, because the handlers still received the right arguments. There are **three** output paths, not two: `CallToolResult` and `ToolDescriptor` are fixed by `#[serde(rename_all = "camelCase")]`, but `daemon_http.rs::handle_tools_call`'s failure arm builds its envelope with `json!({…})` and bypasses both structs — fixing the structs alone left that one broken. Don't confuse `CallToolContent`'s `rename_all = "snake_case"` with this: that one controls the `type` **tag**, whose only variant is `text`. Five regression tests sit in `mod_test.rs`, two of them source-level (`include_str!` over `daemon_http.rs`, skipping comment lines so the file's own prose about the bug can't trip them) because no functional test can observe this class of defect.

**An MCP client must not hardcode a daemon port.** `simple-post mcp` defaults to `--port=0`, so the OS-assigned port changes on every restart and a hardcoded `http://127.0.0.1:<port>/mcp` endpoint silently dies with the next restart — which also means the user cannot change `mcp.policy` without breaking their client's connection, since changing the policy requires a daemon restart. `simple-post-mcp.exe` does **not** solve this on its own: it ignores `mcp.port` and posts to `--url`, which it joins as `{base_url}/mcp` (passing `…/mcp` yields `/mcp/mcp` → 404). The arrangement with no moving parts is **stdio bridge → `serve-web` on its fixed default port 4173**, whose `/mcp` route runs the same `mcp::dispatch`: the client config holds only `command` + `args`, so there is no port in it to drift.

**`preferences.value` holds a JSON-encoded value, not the bare string.** `db::preferences::set` runs `serde_json::to_string`, and every reader runs `from_str` on the result — writing the literal `full_access` instead of `"full_access"` fails to parse, and `mcp_policy` treats an unrecognised value as `ReadOnly` with no error anywhere. The symptom is `tools/list` staying at 16 tools no matter what you wrote to the DB.

**IME guard.** Global shortcuts in `src/App.tsx` must check `e.isComposing`, else CJK IME Enter fires requests.

**The tab strip's active-indicator is derived per frame, never measured once.** `WorkspaceTabs.tsx` keeps one persistent bar at strip level and, while anything that can move a tab may be animating, re-reads the active tab's *live* rect every animation frame and eases toward it (`BAR_APPROACH` / `BAR_SETTLE_MS`). Do not "simplify" this back to `offsetLeft` + `gsap.to`. Three things move those tabs and all three can be mid-flight at the moment a one-shot measurement is taken: the Flip tween (with `absolute: true` every tweened tab reports its **pre-commit** position), the CSS width transition on tab mode change (200ms, changes widths *and* every neighbour's offset), and the strip's `scrollLeft`. Measuring once is what produced the bar drifting to the wrong x and keeping a stale width when tabs were closed. The bar's x is in **content** coordinates — add `strip.scrollLeft` back, or it drifts by exactly the amount scrolled.

**A Tauri command's args are the REST body, flattened field by field.** `#[tauri::command]` binds each parameter **by name** (the macro runs it through `to_lower_camel_case` to get the payload key) — it never deserializes the payload. The renderer sends one flat camelCase object in both shapes, and the REST side feeds the whole thing to `Json<SomeOpts>`, so the parameter list must spell out that struct's fields one by one. Writing `opts: ImportPreviewOpts` instead compiles, leaves every Rust test green, and keeps the web shape perfect — then fails *every* desktop call with `invalid args … missing required key opts`. The regression guards are `src-tauri/src/commands/interchange_test.rs` (source shape, renderer keys, and serde's view of the names, all compared against `dto.rs`) and `crates/simple-post-server/src/web_api/routes/interchange_test.rs` (real requests).

**Semantic token pairing — a `-foreground` token is a colour for text *on* the saturated fill, not on a surface.** `--destructive-foreground` exists to sit on the solid `--destructive` fill, and it **swaps polarity** between scopes: `0 0% 100%` (white) in light, `0 0% 10%` (near-black) in dark, because `--destructive` itself swaps with it (`5 59% 44%` dark red ↔ `354 100% 80%` light pink). Pairing it with a *tint* of that fill therefore breaks one scope: `bg-destructive/10 text-destructive-foreground` is white-on-pale-pink in light mode and merely acceptable in dark. Two correct shapes: **solid** `bg-destructive text-destructive-foreground` (both tokens together, ~4.8:1, nothing overrides either), or a tinted surface with `--destructive` as the text — it is the only token that lightens in the dark scope, so it reads on a 5–10% tint in both. `success` / `warning` are the opposite case: their `-foreground` **is** the text tier (30% light / 75% dark) and the base value only reads as a border, which is why those badges use `bg-success/15 text-success-foreground`. `.alert-error-inline` in `globals.css` and `IconTile`'s `danger` tone both carry the second shape; copy either, not the pairing.

**Reverse-proxy base path is a runtime fact, not a build constant.** `serve-web --public-base-path /sp` `nest`s the *entire* router under the prefix — `/api/*`, `/mcp`, and the three health probes all move to `/sp/…` together. Two consequences that are easy to get wrong:

- `vite.config.ts` sets **no `base`**, so `vite build` emits root-absolute asset URLs (`<script src="/assets/index-<hash>.js">`), and every `WEB_ROUTES` path is root-absolute (`/api/projects`). Neither can be corrected at build time: in the container the prefix arrives as `SIMPLE_POST_PUBLIC_BASE_PATH` at **run** time and one image has to serve both shapes. So `static_files::shell_with_base` rewrites the shell's root-absolute `src`/`href` per response and injects `window.__SIMPLE_POST_BASE__`, which `readApiBase()` in `src/lib/tauri-commands.ts` reads to prefix API calls. **Never "fix" a base-path report by adding `base` to `vite.config.ts` or an nginx rewrite** — those reintroduce a second place that has to agree with the first.
- `/healthz` moves with everything else, so any probe hardcoded to the bare root 404s in exactly the deployment that sets a prefix. The image's healthcheck script reads the same env var for this reason.
- There is **no** `<base href>` tag, and there must not be one: it does not affect a root-absolute `src`, so it would look like a fix while changing nothing.

The regression net is `scripts/test-web-basepath.mjs`, which parses the served shell and actually requests every URL it finds. Its earlier version only asserted the *server* nested correctly (`/sp/api/…` → 200, bare → 404) and never looked at what the browser would ask for — which is how a deployment where the shell loaded and every API call 404'd could pass. Assert on the shell's real references and their content-types; `200 text/html` for a `.js` file is the ServeDir fallback, not an asset.

**A route named in `auth::is_public_path` but never registered answers `200` with the SPA shell.** The auth bypass list and the route tree are two places that have to agree, and nothing made them. `/healthz` sat in that list since the beginning (comment: "legacy, kept for backward compat") with **no `.route("/healthz", …)` anywhere** — so at the root it fell through to the ServeDir fallback and returned the index with `200 text/html`, and under a base path it 404'd. The container `HEALTHCHECK` passed the whole time, because it only grepped for `200 OK`. A probe that cannot fail is worse than no probe: **grep for the response body**, not the status line. Two assertions catch this class — `is_public_path` membership is not route existence, and a probe should assert the thing it is named after.

**OpenAPI.** `public_route_specs()` in `crates/simple-post-server/src/web_api/spec/table.rs` (re-exported from `web_api/spec/mod.rs`) is the single source of truth; internal routes (`/api/mcp/*`, `/api/preferences`) are intentionally undocumented. `node scripts/dump-openapi.mjs` renders that table as an OpenAPI 3.1 document on stdout — pipe it wherever you want, e.g. `node scripts/dump-openapi.mjs > openapi.yaml`. It has no checked-in output since `docs/` was removed.

**Traps a generated spec cannot express**, kept here now that `docs/http-api-reference.md` is gone:

- axum path params are `{id}` — the same form the OpenAPI spec itself uses, so a path copied out of `openapi.yaml` registers correctly and the old「spec 用 `{id}`、axum 用 `:id`，抄错就静默变字面量段」的分歧已不存在。两条 `RouteSpec` 与 `.route()` 共用同一批常量，改一处即可。
- The error envelope is stable: `{ "code": <snake_case>, "message" }`. The `code` is the part to branch on — treat it as the contract and `message` as human-facing text. Note the frontend currently does **not** branch on it: `invokeCmd` folds `code` into the thrown message (`HTTP 400 POST /api/… [validation] …`), so a caller that needs to distinguish "not found" from "denied" must parse the string or add a typed branch. Don't widen that string-formatting into more call sites.
- The auth matrix: `/api/healthz`, `/mcp/healthz` and `/healthz` are always unauthenticated, as are `/assets/*` and the SPA shell — a browser cannot attach `Authorization` to a `<script type="module">`.
- The openapi-diff comparison is the regression guard for any `web_api/` route-tree refactor: regenerate before and after, and a route that vanished shows up as a missing path rather than a failing test.

## Runtime/Tooling Preferences

- **Node `>=20 <23`** (root `package.json` engines); package manager is **npm** (lockfile v3). No pnpm/yarn/bun — do not add their lockfiles.
- Root `package.json` declares **no workspaces**, and there is no second npm package: the `simple-post-mcp` bridge ships only as a compiled binary (release artefact / `cargo install`). Anything an AI client needs is reachable over the daemon's HTTP endpoint, so no registry publish path exists.
- **Rust**: edition 2021, MSRV **1.87**, toolchain channel **`stable`** with `rustfmt` + `clippy` (`src-tauri/rust-toolchain.toml`). The floor is set by `rquickjs`, the request-script sandbox: only it gives a real wall-clock interrupt *and* a memory ceiling, which is what issue #7 asks for. Track `stable` so edition-2024 transitive deps (clap 4.6+, etc.) compile; if you need a pinned baseline, set `channel = "1.87.0"` or newer and run `rustup toolchain install` first.
- TypeScript path alias `@/*` → `src/*`; `moduleResolution: bundler`, `noEmit` (type checks run via `npm run typecheck` / `tsc -b`, also embedded in `npm run build`).
- Workspace builds output to `<repo>/target/`, not `src-tauri/target/`.
- **Line endings: LF everywhere** — `.gitattributes` (`* text=auto eol=lf`) overrides `core.autocrlf`; `.editorconfig` mirrors it for editors (UTF-8, final newline, trim whitespace, 2-space default / 4 for `*.rs`, Markdown keeps trailing spaces). Only `*.bat` / `*.cmd` stay CRLF.
- **Prettier scope**: `*.md` and lockfiles are in `.prettierignore` — hand-maintained prose stays byte-stable. There is no longer a generated `docs/openapi.yaml` in the tree (`docs/` was removed); if you render one, put it outside the repo or add it to `.prettierignore` yourself.
- Windows-first: PowerShell helpers in `scripts/*.ps1`. When writing UTF-8 files from PowerShell, specify `-Encoding utf8NoBOM` — 5.1's default ANSI encoding corrupts UTF-8 and can break `rustc`.
- Multi-worker convention: parallel workers deliver code only; end-to-end/browser verification is done once by the main session. The reason is shared-resource contention — several agents on one dev server, one browser session and one writable file collide, and the symptom looks like a flaky failure rather than a conflict.

**No Vitest/Jest/React Testing Library.** Frontend tests use the Node built-in runner via `tsx --test` + `node:assert/strict`.

|---|---|---|

| Rust | `cargo test --workspace` / `-p <crate>` | sibling `#[path]` test modules — see below |
| MCP end-to-end | `npm run test:mcp` | `scripts/mcp-integration.test.mjs` (needs compiled `simple-post` binary) |
| Web auth integration | `npm run test:web:auth` | `scripts/test-web-auth.mjs` (needs compiled binary; spawns two phases — open + locked) |
| Web base-path integration | `npm run test:web:basepath` | `scripts/test-web-basepath.mjs` (needs compiled binary; `--public-base-path /sp`) |
| Web perf bench | `npm run perf:bench` | `scripts/perf-bench.mjs` (p50/p95/p99 over N hits against a **running** server; `--target URL` to point elsewhere; `--assert` gates 200ms p95) |

| Store invariant check | `npx tsx scripts/_verify_store.mjs` | selector stability, cascade delete, prefs persistence |

Key facts:

- **Test file placement — frontend.** Every test lives in a `__tests__/` directory beside the code it covers: `src/lib/__tests__/*.test.ts` and `src/stores/__tests__/*.test.ts`. The file is still named after the module (`http.test.ts` for `http.ts`), not after the folder. `__tests__` is a recognised convention (Create React App / Angular lineage) rather than *the* standard — co-location is the more common modern React default — but it is a legitimate one, and consistency inside this repo is what matters. The double underscore marks the directory as non-shippable without relying on a bundler honouring any name.
- **Test file placement — Rust.** There is no `__tests__` equivalent and no way to add one: Rust's module system resolves a file's location from the module path, so a test-only directory is not discoverable. The two options are the inline `#[cfg(test)] mod tests { … }` and a sibling file reached through `#[path]`. This repo uses the sibling form everywhere except four files still inline (`src-tauri/src/main.rs`, `crates/simple-post-server/src/{auth,main}.rs`, `crates/simple-post-server/src/web_api/static_files.rs`) — match the dominant form when you add tests:
  ```rust
  #[cfg(test)]
  #[path = "projects_test.rs"]
  mod tests;
  ```
  `super` resolves identically from a `#[path]` module, so the extracted body keeps its `use super::*;` unchanged and `cargo fmt --all` re-indents it. `#[path]` rather than the Rust 2018 `projects/tests.rs` submodule directory, so the pairing stays visible in directories that are otherwise flat `*.rs` files. When splitting one, **match the braces — do not assume the block's closing brace is the last line**: `db/mod.rs` has `pub mod test_counter` *after* its `mod tests`, and swallowing that tail would compile a `#[cfg(test)]` test helper into the library.
- **`npm test` auto-discovers `src/**/*.test.ts`** through `scripts/run-tests.mjs` — no hardcoded list, new test files are picked up automatically. In `--watch` mode the list is captured at spawn time: restart `npm run test:watch` after adding/renaming a test file. Single file: `npx tsx --test path/to/foo.test.ts`.
- **A test that resolves the module under test at runtime survives neither a move nor a rename.** `tauri-commands-shell.test.ts` probes `IS_TAURI_SHELL` in a `spawnSync` child because that flag is frozen at module-eval time, and resolves the module with `new URL('../tauri-commands.ts', import.meta.url).href`. That URL is relative to the *test file*, so moving the test silently broke it until the path gained its `../`. Typecheck and lint both passed on the broken version — only the child process failed. Grep for `import.meta.url` and `__dirname` whenever a test file changes directory.
- ESLint scoping decisions (in `eslint.config.js`): `no-explicit-any` off under `**/*.test.ts` and `**/__tests__/` (deliberately loose mocks); `no-require-imports` off for `.mjs`/`.cjs` tooling; names starting with `_` are sanctioned unused placeholders; `react-hooks/rules-of-hooks` is **error** — `HttpTester`'s hooks were hoisted above its `if (!endpoint)` early return to satisfy it (never put hooks after an early return).
- Headless store tests need `src/stores/__tests__/_browser-shim.ts`: installs Map-backed `localStorage` (Node 22 ships a methodless native `localStorage` that crashes otherwise), `document.visibilityState` emitter, timers, and `mockIPC`, and sets `window.__TAURI_INTERNALS__ = {}` *before* module eval so `IS_TAURI_SHELL === true`.
- **No seed data ships with the app.** `db::init` runs `schema.sql` and stops — a fresh install is empty. `crates/simple-post-core/src/db/fixtures.json` is **test-only**: it is reachable solely through `#[cfg(test)] pub(crate) mod test_support` (`init_seeded` / `seed`), which does not exist in a production build. Because `test_support` is `pub(crate)`, sibling crates cannot use it — the `endpoint_send_tests` module in `src-tauri/src/commands/endpoint_send_tests.rs` builds its own rows through the public CRUD API instead. There is **no** TS mock-data module; store tests build their own fixtures inline.
- Rust DB tests isolate via `fresh_pool()` → temp-dir SQLite keyed by atomic counter + PID (`crates/simple-post-core/src/db/mod_test.rs`, the `#[path]` module of `db/mod.rs`).
- Store custom hooks (`useActiveProject`, …) throw outside a React render; in Node, read state with `useAppStore.getState()`.
- No React component/DOM tests; no coverage tooling configured (c8/nyc/tarpaulin absent).
- **Race-prone component logic is still pin-able here.** With no component/DOM tests, move the logic that races (debounce, cancellation, generation guards) into a React-free module beside the component and test *that* module; the component keeps only the state writes. `src/features/dynamic-variables/node-search.ts` + `__tests__/node-search.test.ts` is the worked example: it injects its timers, so the test drives the schedule instead of waiting out the debounce.
- Integration tests need a built binary — `npm run test:mcp` exits code 2 without it; use `npm run build:tests` (same preflight, exits 2 as well) when a gated variant is wanted.
- The same applies to `npm run test:web:auth` and `npm run test:web:basepath`: both require `target/debug/simple-post.exe` (or `--release`) on disk. `npm run perf:bench` is the exception — it resolves no binary and instead `fetch`es a **running** server (default `http://127.0.0.1:4173`, override with `--target`), so the server must be up separately.
